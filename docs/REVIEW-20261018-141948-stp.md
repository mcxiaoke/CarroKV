## 四、本次复审新发现问题

### 4.1 新发现 P1（10 项，按危险程度排序）

#### N-X1【.NET】`IncrementInt64` 原子性回归——规范明文"P0 原子累加器"被并发破坏
- **位置**：`src/dotnet/src/Ckv/Db.cs:2802-2850`
- **问题**：read-modify-write 被拆成"读锁内读值（2809-2829）→ 预计算 newVal（2831）→ ExecuteMutation 写锁内应用预计算值（2836-2849）"。两个线程并发 `IncrementInt64(k, 5)`（现值 10）会双双算出 15，**最终值 15，一次累加静默丢失**。
- **回归证据**：`git show 4066a98`（批次三）中整个 RMW 在同一把写锁内；`a814907`（批次四两阶段重构）将其拆分后原子性丧失。批次四只修了"落盘失败 double increment"（单线程用例），未覆盖并发增量。
- **规范违反**：KV-DB-DESIGN-SPEC.md:346 明文标注该操作为"**P0 原子累加器**"，§4.1.1 强制进程内线程安全。
- **跨语言核对**：Rust（`db.rs` increment 闭包内读+算）、Go（`db.go` executeMutation 闭包内读+算）、Kotlin（`CkvDb.kt` executeMutation 内读+算）、Dart（单线程同步）均原子——**.NET 是五语言唯一离群值**。
- **建议**：读值移入写锁临界区重算，或 applyMem 阶段基于当前值计算；补双线程并发累加回归测试。

#### N-X2【Rust / Kotlin】AOL + Deferred 后台刷盘无代际守卫，`is_dirty` 被误清——掉电可丢已确认数据
- **位置**：Rust `db.rs:556-567`（AOL 分支 fsync 后**无条件**清 `is_dirty`，计划阶段 generation 传占位 0）；对照快照分支 `db.rs:582-595` 有 `dirty_generation != generation` 守卫。Kotlin `CkvDb.kt:689-703` 同构未修（既往 P1-27）。
- **竞态序列**：① worker 计划阶段读到 `is_dirty=true` → ② worker 完成 `sync_all()` → ③ 写线程 append 新帧并置 `is_dirty=true`（非 Immediate 下只 flush 不 fsync）→ ④ worker 取写锁清掉 `is_dirty` → ③ 的帧再无 fsync 机会，`close()` 也因标志为 false 而跳过 → **掉电/OS 崩溃丢失已确认写入**。
- **跨语言核对**：Go（`db.go:424`）、.NET（`Db.cs:513`）的刷新入口均有 generation 守卫；Dart 单线程无此竞态。**Rust 与 Kotlin 两语言敞口**。
- **建议**：AOL 分支同样采样 `dirty_generation`，清标志前比对；不一致则放弃本次清旗（数据已 fsync，无需重做）。补 AOL+Deferred 后台竞态测试（现有 `deferred_flush_race_test` 三用例均为快照引擎，完全无防护网）。

#### N-X3【Kotlin】SNAPSHOT + MANUAL 每次写立即全量落盘——跨语言语义分叉 + Manual 契约失效
- **位置**：`CkvDb.kt:1143`（`if (options.syncMode == SyncMode.DEFERRED)` 才分流纯内存路径，MANUAL 落入 else 两阶段提交）
- **问题**：SNAPSHOT + MANUAL 下每次 put/delete 都触发全量序列化 + fsync + 双轮转。API-SPEC.zh.md:76 明确"`Manual`：内存只写，完全由用户调用 `flush()` 时才落盘"。
- **跨语言核对**：Rust（`db.rs:843` `Deferred || Manual` 合流）、Go（`db.go:2464` else 注释 "SyncModeBatch (Deferred / Manual)"）、.NET（`Db.cs:2084` 条件为 `SnapshotAtomic && Immediate`）、Dart（`db.dart:981/1041` 仅 immediate 分流）**四语言均将 Manual 与 Deferred 同等处理；Kotlin 是唯一离群值**。
- **测试掩盖**：`SyncModeTest.kt:26-60` 的两个 Manual 用例在两种实现下断言全部相同，缺陷无法被现有测试发现。
- **建议**：条件改为 `syncMode == IMMEDIATE` 才走两阶段；补"MANUAL 下连续写后文件长度不变、flush 后才落盘"的断言。

#### N-X4【Kotlin】两阶段提交 Phase 2 序列化实时 `namespaces` 而非 Phase 1 快照——DEFERRED 写交错可丢已确认写
- **位置**：`CkvDb.kt:888-890`（`buildSnapshotBytes` 内 `namespaces[ns]!!`，`targetNamespaces` 参数被弃用）
- **问题**：IMMEDIATE 写 Phase 2 在无锁状态下序列化，本应序列化 Phase 1 提取的 CoW 快照，实际读实时 map。DEFERRED 写只取 `rwLock.write` 不取 flushGate，可在 A 的 Phase 2 与 Phase 3 之间落地：A 的快照不含 B 的写，A 的 Phase 3 却将 `isDirty=false`（`:1230`）——**B 那次已确认的 DEFERRED 写既不在磁盘、脏标记又被误清，重开/掉电后静默丢失**。若 B 是 `dropNamespace`，`namespaces[ns]!!` 抛 NPE 被包装成 `IoError`，A 的写被误判失败并回滚。
- **建议**：`:890` 改为从快照 map 取值；补交错回归测试。

#### N-X5【Go】轮转失败时删除 `.tmp`——违反规范 §4.2 且与同文件 commitFlush 自相矛盾
- **位置**：`db.go:2541-2547`（`executeMutation` 阶段 3 轮转失败 `_ = os.Remove(tmpPath)`）
- **问题**：规范 §4.2 明确要求"重试耗尽仍失败，抛出 `IoError`，**且必须保留 `data.db.tmp` 不删**，以供后续自愈"。同一文件的 `commitFlush` 在同样失败下保留 `.tmp`（`:2143-2153`）。最危险子情形：第一个 rename（`.db`→`.bak`）已成功、第二个失败——此时删 `.tmp` 导致主库缺失，下次 Open 落入"主库缺失 + `.bak` 存在"的拒绝分支，新代数据无从晋升。与 P1-19 修复方向（保留 `.tmp`）背道而驰。
- **建议**：与 commitFlush 对齐——轮转失败保留 `.tmp`、置 `isDirty=true`、返回 `IoError`。

#### N-X6【Dart】`flushAsync`/`backupAsync` 无互斥——await 点插入同步写可覆盖新提交（数据丢失）
- **位置**：`db.dart:772-805`（`_commitFlushAsync` 序列化后有 await 挂起点 `:782/784/786/789`）
- **问题**：`final f = db.flushAsync(); db.putString(...); await f;` 序列化为：① flushAsync 序列化旧状态 → 挂起；② putString 同步提交新状态（含自己的 `.tmp` 轮转）；③ flushAsync 恢复，把**陈旧数据**写入 `.tmp` 并 rename 覆盖 `.db` → 步骤②的已提交写入被静默回滚。两个并发 flushAsync 还会以 `FileMode.write` 交替写同一 `.tmp`。CHANGES-20261018 声称五语言"阶段二仅持 flushGate/flushMutex 串行"——**Dart 侧没有任何 gate/mutex**。现有测试 `batch_four_pipeline_test.dart:118-137` 只测串行 await。
- **建议**：引入 `Future _flushGate` 串行化（serialize 前取 gate、rename 后释放）；补交错回归测试。

#### N-X7【Dart】写路径无条件 CoW 克隆——批次四引入的性能回归
- **位置**：`db.dart:1071-1080`（及 delete 路径 `:1521-1525`、batch delete `:1693-1697`）
- **问题**：`_getOrCreateStoreForWrite` 现在只要 `clonedInTx` 未含该 ns 就 `store.clone()`，删除了批次三之前的 `_snapshotCount > 0` 守卫（`git show 4066a98` 可见原守卫）。**即使没有任何存活快照，`putString` 也要拷贝整个命名空间有序列表**；AOL 引擎"稳态 ~0.18ms/写且与规模无关"的卖点被重新变成规模相关，直接违背引擎选型文档。现有 CoW 测试恰好先建了快照，绕开了回归路径。
- **建议**：恢复 `if (_snapshotCount > 0 || !clonedInTx.contains(normNs))` 条件克隆；delete/batch delete 三处同步修改。

#### N-X8【Dart】AOL + strictCompaction：压缩失败回滚已落盘的变异——内存/磁盘三重不一致
- **位置**：`db.dart:1032-1040` + `:890-915`
- **问题**：`_appendEntries`（帧已持久化成功）→ applyMem → `_maybeCompactAfterWrite` → strictCompaction 失败 rethrow → 被 `_applyMutation` catch → `_rollback`。此时磁盘日志已含该帧，内存却回滚：会话内读旧值；进程崩溃后重开得到新值（帧被重放）；若之后 flush/compact 则以旧内存覆盖日志、**写入永久丢失**。D2 决策注释自己论证了"变异已持久所以报错会诱导对已成功写入的重试"。
- **建议**：strictCompaction 路径跳过 `_rollback`；补内存/磁盘一致性测试。

#### N-X9【.NET】ExecuteMutation 关闭检查位于 `_flushGate` 之前——Dispose 可插入导致"关闭后落盘"
- **位置**：`Db.cs:2078-2079`（ThrowIfDisposed/CheckWritable）→ `:2087`（gate.Wait）→ `:2099-2105`（phase 1 只复检 ReadOnly，不复检关闭态）；IL 实证执行序。
- **时序**：写线程通过关闭检查 → 另一线程 Dispose 完整走完 CloseRoot（置 `_isClosed`、最终刷盘、**释放跨进程内核锁**、移除注册表）→ 写线程取得 gate 后继续写 `.tmp` 并轮转 → 数据库文件在关闭后被"复活"，且该写入**不持有跨进程内核锁**，另一进程可合法打开同库 → **双写者截断风险**。加重情节：AOL 分支 `Db.cs:2208` 在写锁之前直接追加帧且不取 gate；Deferred/Manual 分支 `:2226-2240` 关闭后仍改内存并置 `_isDirty=true`，而 CloseRoot 最终刷盘已结束 → 该次写入静默丢失且调用方得到成功返回。
- **建议**：phase 1 写锁内、AOL 追加前、else 分支写锁内统一复检 `_root._isClosed`；补"并发 Dispose vs 写"竞态测试。

#### N-X10【.NET】同进程并发首次 Open 同一路径 → 干等 LockTimeoutMs 后抛 LockedError——单例契约破产
- **位置**：`Db.cs:662-712`（两线程同时首开：双双读过空注册表 → 双双新建 → 一方拿内核锁，另一方重试至超时 10s 后 `LockedError`）；"注册竞争恢复"逻辑 `:684-712` 实际不可达。
- **规范违反**：`Db.cs:600-615` 文档承诺"同路径多次调用 Open 统一复用并返回门面句柄"。REVIEW §测试缺口早已列名"同进程并发 Open"，至今零覆盖。
- **建议**：取跨进程锁之后、InitAndRecover 之前复检注册表，命中活跃实例则释放本轮锁并返回门面；补双线程并发首开测试。

## 十、结论与建议

1. **是否"存在问题"**：是。本次复审新识别 10 项 P1（其中 6 项由近期写路径重构/便利 API 变更引入或暴露）、约 30 项 P2、约 25 项 P3；既往 40 项 P1 中约 12 项仍未收口。最关键的三类：**并发增量/写入原子性缺口**（.NET increment、Dart flushAsync、Kotlin Phase2）、**AOL 持久性守卫缺失**（Rust/Kotlin）、**规范硬性条款五语言集体欠账**（HeaderFlags、`.corrupt`、Snapshot 释放语义、UTF-8 过滤）。
2. **是否"有遗漏"**：既往审查与修复记录整体可信度较高（P0 全修复且有测试），但存在三类遗漏：① 批次四重构的**跨语言对比视角缺失**——同一重构在五语言落地质量不均（如 Manual 分流四国一离、代际守卫两国缺失、.NET increment 被拆分），单语言审查无法发现；② **CHANGES 声明与代码/CI 实际不符**两处（P1-16"彻底修复"、extended job"晋升 PR 门禁"）；③ **测试缺口**约 45 处，其中"同进程并发 Open"自 10-17 审查点名至今零覆盖。
3. **最紧要行动**：按第八节第一批 10 项实施（均为小到中等工作量，预计可在一个迭代内完成），完成前不建议将默认 `SnapshotAtomic + Immediate` 模式用于生产关键数据；`AppendOnlyLog` 用户在 Rust/Kotlin 上应临时提高 flush 频率或显式 `flush()` 作为缓解。
4. **本报告未覆盖项**：未执行全量测试套件（遵守只读约束，运行时竞态结论为静态推断，建议修复后用 `-race`/并发用例复核）；未审查 benchmarks 与 examples 的业务逻辑；`src/rust/temp`、`temp/` 下未跟踪文件不在审查范围。
