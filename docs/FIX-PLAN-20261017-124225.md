## 0. 修复原则

1. **先止损后优化**：数据丢失/损坏类（P0）→ 契约一致性 → 健壮性/内存 → 工程基线 → 架构决策。任何阶段不得跳过前一阶段门禁。
2. **测试先行**：每个修复先写可失败（red）的回归测试，再改实现。项目已有此纪律（C/D/G 编号 + 回归测试文件），本计划延续并新增 C22 编号。
3. **规范先行**：跨语言行为变更必须先更新 `KV-DB-DESIGN-SPEC.md` / `API-V1-FREEZE.md`（或新立 ADR），再动代码；黄金向量（`testdata/*.db`）是跨语言契约的字节级门禁。
4. **最小爆炸半径**：不借修复之机重构无关代码；热路径改动（序列化/迭代器）必须带前后基准对比。
5. **可回退**：每个修复独立提交、独立测试；任一修复引发回归，revert 单条提交即可，不影响其他修复。

## 2. 修复方案详设

### FIX-01 后台刷盘竞态（P0，数据丢失）— 最高优先

**根因**（R2）：C16 两阶段刷盘（读锁克隆 → 锁外写 `.tmp` → 写锁轮转）缺少两道保护：① 无互斥导致两个提交者同时写同一 `.tmp`；② 轮转前不校验数据代际，导致陈旧快照被轮转上位并清除他人的 dirty 标志。

**方案**（Rust `db.rs` + .NET `Db.cs` + 规范增补 C22）：

1. **专用 flush 互斥锁**：`DbInner` 增加 `flush_mutex: Arc<Mutex<()>>`（.NET：`SemaphoreSlim(1,1)`）。SnapshotAtomic 模式下**所有**提交路径（`bg_flush_step` 快照分支、`flush()`、`close()`、`compact()`）序列化前必须持有。
   - 锁序铁律：**`flush_mutex` 永远先于读写锁获取**。AOL 自动压实路径（持写锁内 `commit_flush`）**不取** flush_mutex——AOL 模式后台线程只 fsync 不碰 `.tmp`，无共享，故无死锁（写者持写锁等 flush_mutex、bg 持 flush_mutex 等写锁的循环等待不存在）。
2. **脏代际校验**：`DbInner` 增加 `dirty_generation: u64`，每次 `apply_mutation` 成功提交时 +1。bg 线程在读锁内记录 `g = dirty_generation` 并克隆数据；序列化（持 flush_mutex、不持读写锁）完成后，在写锁内轮转前校验：
   - `!is_dirty` 或 `dirty_generation != g` → **丢弃本次 `.tmp`、不轮转、不清 dirty、不动 `last_known_disk_state`**，直接返回（下一 tick 或显式 flush 会以新状态重试）；
   - 校验通过才轮转并更新账本。
3. **显式路径简化**：`flush()`/`close()`/`compact()` 持 flush_mutex + 写锁完成序列化与轮转（与现状相同，只是多一把互斥）；`close()` 已在 join 后台线程后执行，天然安全。
4. **`.NET Dispose`**：去掉 timer 回调等待的 1s 上限（循环等待至回调结束），最终 flush 失败经 `OnWarning("onFinalFlushFailed", …)` 上报而非静默吞掉（与 FIX-06 合并实施）。
5. **规范增补**：`API-V1-FREEZE.md` 新增 §3.19（C22）：固化 flush 互斥 + 代际校验契约，五语言一致；同步修订 §3.16。

**回归测试**（先红后绿）：
- Rust `tests/deferred_flush_race_test.rs`：Deferred + SnapshotAtomic，用注入延时 hook（或极大 value 拉长序列化窗口）构造确定性时序：后台 flush 进行中 → 写入 W → 显式 `flush()` → 等后台轮转完成 → `close()` → **重开验证 W 仍在**；另测反向（先显式后后台）与并发双 `flush()` 不损坏。
- .NET `DeferredFlushRaceTests.cs` 同构；探针复用 R1 的 `temp/probe`、`temp/netprobe` 做 4 象位矩阵。
- 锁序死锁测试：AOL 模式下写线程 + 后台线程 + 显式 flush 三线程并发 30s 无卡死。

**风险**：低。改动集中在提交路径；默认 Immediate 模式行为不变（bg 线程不启动）。

### FIX-02 跨进程锁语义（P0，契约）

**(a) Rust `lock.rs`**：
- 把 `open(&lock_path)` 纳入同一 deadline 退避循环；Windows 上 `raw_os_error ∈ {5, 32, 33}`（访问被拒/共享冲突/锁冲突）与 Unix `EAGAIN/EWOULDBLOCK` → 重试至 `lock_timeout_ms` 后抛 `DbError::Locked`（错误类型对齐冻结契约 §1.3）；其余 I/O 错误立即抛 `DbError::Io`。
**(b) .NET `LockFile.cs`**：锁文件句柄 `FileShare.None` → `FileShare.Read | FileShare.Write | FileShare.Delete`（持有方的共享模式必须允许他人 open + 经 `LockFileEx`/flock 竞争；互斥由内核锁保证，不靠共享拒绝）。
**(c) Rust `close()`**：显式 `self.lock.take()` 释放并置空；`Drop` 保持幂等释放。
**(d) 规范**：重写 `KV-DB-DESIGN-SPEC.md §4.1.2` 为 C9 内核锁协议（flock/LockFileEx、连接生命周期持有、共享模式要求、无窃取无判活）；删除 §5.1.1 的 `forceUnlock` 或标注废弃。
**回归测试**：`lock_protocol_test.rs` 增加异语言象位（CI 中 Rust↔.NET 互持，四象限：持锁/竞争/close 后竞争/进程消亡后竞争）；Rust 单测"close 后同进程可立即重开"。

**风险**：低~中。(b) 是跨语言行为变更，须与 Rust 同批发布，否则新旧混用仍会出现单侧快速失败——**发布说明中强制要求双语言同版本**。

### FIX-21 AOL 压实阈值悬崖（P0，性能；2026-10-17 实证新增）

**根因**（`db.rs:2044-2071` ↔ `Db.cs:1428-1445`）：`maybe_compact_after_write` 的触发条件是**绝对文件大小**超过阈值：

```rust
if new_file_size >= self.options.compaction_threshold_bytes {   // db.rs:2060
    return self.attempt_compaction();                          // 全库重写 + 轮转
}
```

压实后文件恰好等于存活数据大小。于是**一旦存活数据 ≥ 阈值（默认 4MB），每一次写都满足条件、都触发一次全库重写**（在写锁内序列化 + fsync + 两次 rename）。死比率触发器救不了它：压实后死比率 ≈ 0。

**今日实测**（`temp/probe/src/bin/steady_state.rs`，AOL + Deferred，每键 1KB，先以关闭压实方式装入再以默认阈值重开测稳态）：

| 存活规模 | 压实关闭（对照） | 阈值 4MB（默认） |
|---|---|---|
| 0.6MB | put 0.183ms（5,478 ops/s） | put 0.167ms（5,991 ops/s） |
| 6MB | put 0.193ms（5,180 ops/s） | **put 24.381ms（41 ops/s）** |
| 20MB | put 0.192ms（5,216 ops/s） | **put 77.453ms（13 ops/s）** |

覆写热键（纯产垃圾）同样 24~79ms/次；批量装入退化为 O(N²)（30MB 装入探针运行 9 分钟未完成被终止）。同步模式无关（Deferred 已无 fsync，代价全是重写）。

**为何此前的评审与测试都没发现**：仓库内全部压实测试都用 `threshold = u64::MAX/2` 或 `u64::MAX-1`（等效关闭）来隔离其他行为；项目自带的矩阵基准（`sync_wal_matrix_bench.rs`）用 128B × 5,000 次 ≈ 640KB，从未跨过 4MB。R1 测 AOL 时明确"关闭自动压实以隔离变量"但未将其与默认值联系；R2（本会话评审）引用了 README"68 万 ops/s"而未做规模验证——两报告在此点上均失查，本计划更正。

**关于"68 万 ops/s"的真相**：该数字来自 AOL + **Manual** 模式（矩阵基准 5,000 次写只在内存暂存、结束一次 flush），且数据集 <4MB。它衡量的是"批量内存写 + 一次落盘"，不是每写持久化吞吐；同口径下 redb 的 `Durability::None` 为 109 万 ops/s——同一"非持久化批量"级别。**每写都落 OS 缓存（Deferred）的实测约 5,200 ops/s（本机 Windows），每写 fsync（Immediate）约 1,500 ops/s（R1 实测）**，README"Immediate→Deferred 仅提升 15~31%"的声明与实测（+233%）不符，项目性能文档需重测重写。

**修复方案**（Rust + .NET + 规范 §4.5）：
1. **触发条件改为"累计追加字节"**：`DbInner` 增加 `bytes_appended_since_compaction: u64`（`append_entries` 中按写出的帧字节数递增；压实成功时归零）。触发：`bytes_appended_since_compaction >= effective_threshold`——精确度量"新数据 + 垃圾"，O(1)，与存活大小解耦。
2. **阈值随存活缩放**（防 WAF 随库增长）：`effective_threshold = max(compactionThresholdBytes, live_payload / 4)`，即任何规模下 WAF ≤ ~5x（当前固定 4MB 在 100MB 存活时 WAF = 25x）。作为默认行为写入规范 §4.5，不新增公开选项。
3. 死比率触发器保持不变（处理存活坍缩场景）；`compaction_threshold_bytes = 0` 仍是总开关。
4. 规范 §4.5 "文件大小（原有）"一行改写为"累计追加字节（含垃圾）"，并记录本次修订依据（本计划编号 FIX-21）。

**回归测试**（先红后绿）：
- `wal_threshold_cliff_test.rs`：默认阈值，装入 6MB 存活（6k×1KB），断言稳态 put p99 < 5ms、且文件在越过 `live + threshold` 前不被重写（用文件大小/`last_known_disk_state` 观测）；
- 垃圾确实超过阈值时必须压实（现有 wal_auto_compaction_regression_test 补充默认阈值用例）；
- O(N²) 装入防护：6MB 装入总时长 < 10s；
- .NET 同构用例；性能回归探针（`temp/probe` 的 steady_state）纳入 CI nightly。

**与 FIX-16 的关系**：此修复使 AOL 模式在任何规模下恢复"摊销 O(1) 写"，方案 B 的必要性随之下降——B 的重心变为读写延迟解耦（压实不阻塞读）与内存/打开时间，而非写路径本身。
