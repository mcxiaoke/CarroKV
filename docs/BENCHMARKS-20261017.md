# CKV 规模与延迟基准（2026-10-17）

> 复现：`cd src/rust && cargo run --release --example scale_profile`（输出在 `src/rust/out/`）
> 数据由探针直接输出，未经手工整理；本文只补充方法与解读。

## 环境

| 项 | 值 |
| :--- | :--- |
| CPU | Intel Core i7-11700 @ 2.5 GHz（8C/16T） |
| 内存 | 32 GB |
| OS | Windows 10 专业版 |
| 工具链 | rustc 1.89（release，`lto` 未开启） |
| 存储 | 本机 NVMe SSD（未单独标注文件系统） |
| 值大小 | 每键 1 KB，键宽 8 字节，单一命名空间 |

## 方法

对 2 / 10 / 50 / 100 MB 存活数据各做五组测量：

1. **装载**：`AppendOnlyLog` + `Deferred`（关闭压实）逐键写入直至目标规模，结束时一次 `flush()`；
2. **打开**：以默认压实阈值重开 5 次，取中位数与最大值（含全文件解析）；
3. **RSS**：打开后进程工作集（Windows `WorkingSet64`）；
4. **稳态写**：AOL + `Deferred` + 默认阈值，覆写既有键 2000 次。此窗口内垃圾量（约 2 MB）不足以触发 4 MB 阈值，因此**不含压实**；
5. **压实暂停**：显式调用 `compact()` 10 次，取 p50/p99——这部分对应「真实压实发生时写锁被占用多久」；
6. **默认模式单写**：`SnapshotAtomic` + `Immediate`（默认配置）连续写 12~25 次，取 p50/p99。

## 解读

**1. AOL 稳态写与规模无关。** 0.17~0.18 ms（约 5,500 ops/s），四档一致——FIX-21 之后追加路径确实是摊销 O(1)。这是"修完 bug 就能扩容"的部分。

**2. 三条线性成本仍在，且斜率可测。**

| 成本 | 斜率 | 100 MB 时 |
| :--- | :--- | :--- |
| 打开（全量解析） | ≈ 13.5 ms/MB | 1.36 s |
| 压实暂停（写锁内 O(存活)） | ≈ 4.2 ms/MB | p99 514 ms |
| 默认模式单写（整文件重写） | ≈ 3.8 ms/MB | 376 ms |

**3. 默认模式不适合大数据集，这是设计而非缺陷。** `SnapshotAtomic` + `Immediate` 每次写都把整库序列化并 fsync：2 MB 时 10.6 ms（约 94 ops/s），10 MB 时 41.8 ms（约 24 ops/s）。它面向的是"小于 2 MB 的配置/凭证/偏好"，在该区间实测与 LMDB 同口径相当。

**4. 内存约为文件的 1.2 倍（Rust）。** 110 MB 文件对应 129 MB 工作集。此前评审记录的 "≈2.23 倍" 是 .NET 实现的数字（每项一个对象、字符串键）；本次**未重新测量 .NET**，文档不应把两者混用。

**5. 50 MB 是当前可承诺的上界，100 MB 属于"能跑但不建议"。** 判据是压实的 p99 暂停：50 MB 为 287 ms，100 MB 为 514 ms——后者已超出"交互式桌面应用可忍受的卡顿"范围，且打开需要 1.4 s。

## 与旧文档的差异

旧 README 称 AOL 适用 "1 MB ~ 100 MB"、并在默认 4 MB 阈值处压实。该说法在 FIX-21 之前会导致存活 ≥4 MB 后每次写都全库重写（6 MB 存活实测 26 ms/写）；修复后压实按垃圾量触发（`garbage >= max(4MB, live/4)`），本表的"AOL 稳态 p50/p99"才成立。

## 未覆盖

- 多线程并发读写、混合负载：不在本库的定位内，未测。
