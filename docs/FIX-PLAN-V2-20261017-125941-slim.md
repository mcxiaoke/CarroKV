## 2. 保留项的实施要点（只写与原计划的差异）

### FIX-01 后台刷盘竞态 — 保留双机制，删掉仪式

**代码定位（已核对）**：`db.rs:404-479`（`bg_flush_step` 读锁内 clone → 锁外写共享 `.tmp` → 写锁内轮转）与 `db.rs:1085`（`flush()` 在写锁内独立写同一个 `.tmp`）。两个提交者 + `is_dirty` 误清均属实。

**不可简化的实测依据**（release / Windows NTFS，含序列化 + 两次 rename + file fsync）：

| 库大小 | 首次 | 稳态中位数 |
|---|---|---|
| 1 MB | 14.8 ms | 9.1 ms |
| 9 MB | 33.5 ms | 35.2 ms |
| 48 MB | 171 ms | 170 ms |

约 3.5 ms/MB，fsync 主导。因此：
- "全流程放写锁内、删掉互斥 + 代际"的简化方案 → **否决**。1MB 就阻塞 9ms，2MB 约 18ms，Deferred 模式失去意义。
- "只加互斥、不加代际" → **否决**。显式 `flush()` 先落盘后，bg 仍持旧快照会覆盖，必须代际校验。

**裁剪项**：
1. 删除原计划 §3.19 独立规范章节 + "锁序铁律"，改为：`DbInner.flush_mutex` 字段上方一段注释 + 一个 `debug_assert`（写锁持有期间不得取 flush_mutex 的反向断言）。契约写进 `API-V1-FREEZE.md` 的现有 §3.16 条目末尾一句话即可。
2. 三套回归测试合并为 2 个用例：
   - Rust `deferred_flush_race_test.rs`：Deferred + SnapshotAtomic，用 10MB value 拉长序列化窗口构造时序 → 后台刷盘中写入 W → 显式 `flush()` → `close()` → 重开断言 W 存在；再测反向顺序。
   - .NET 同构 1 个用例。
3. 删除"AOL 模式三线程并发 30s 无死锁"独立测试 → 并入 `concurrency_test.rs` 已有的并发用例（跑 3s 即可）。

### FIX-02 跨进程锁 — 保留 (a)(c)，删除 (b)

**删除 (b)**：不修改 .NET `LockFile.cs` 的 `FileShare.None`。
理由：`KV-DB-DESIGN-SPEC.md:13` 明确不支持多进程并发读写；锁的职责是"第二者快速失败"。把 `FileShare.None` 放开成 `Read|Write|Delete` 会使 .NET 的强制互斥退化为 advisory，为不存在的场景牺牲单实例保护。Windows 上两种实现组合后仍能正确 fail-fast：
- Rust 持 flock、.NET 打开 → `LockFileEx` 失败 → `Locked`；
- .NET 持 `FileShare.None`、Rust 打开 → `ERROR_SHARING_VIOLATION(32)` → 归入 (a) 的重试/错误映射 → `Locked`。

**保留 (a)**：`lock.rs:38-50` 的 `open()` 纳入 deadline 退避循环，`raw_os_error ∈ {5,32,33}` / `EAGAIN` → 重试至超时后 `DbError::Locked`，其余 I/O 立即 `Io`。
**保留 (c)**：`close()` 显式 `self.lock.take()`；`Drop` 幂等兜底。

**裁剪项**：
1. 删除"异语言四象限互持矩阵"。改为 2 个用例：`close()` 后同进程立即可重开；第二实例打开时拿到的错误类型是 `Locked` 且耗时 ≈ `lock_timeout_ms`。
2. 规范 §4.1.2 不改写为完整内核锁协议，只补 3 句：独占语义 / fail-fast / 超时与错误类型映射。
3. `§5.1.1 forceUnlock` 直接删除（原计划给了"删除或标废"两个选项，取删除）。

### FIX-21 AOL 压实阈值悬崖 — 换一个更简单的修法

**已独立复核**（13:33 复跑 `temp/probe/src/bin/steady_state.rs`，AOL + Deferred，每键 1KB）：

| 存活规模 | 压实关闭 | 默认阈值 4MB |
|---|---|---|
| 0.6 MB | 0.192 ms（5,208 ops/s） | 0.180 ms（5,553 ops/s） |
| 6 MB | 0.210 ms（4,762 ops/s） | **26.1 ms（38 ops/s）** |
| 20 MB | 0.217 ms（4,617 ops/s） | **86.0 ms（12 ops/s）** |

**作用域已确认**：`maybe_compact_after_write` 只在 `apply_mutation` 的 AOL 分支被调用（`db.rs:2255`），默认 SnapshotAtomic 路径不经过它 → 默认配置不受影响。.NET `MaybeCompactAfterWrite`（`Db.cs:1428-1445`）条件同构。

**与原计划的差异（重要）**：原计划 FIX-21 的方案是"新增 `bytes_appended_since_compaction` 计数器 + 阈值随存活缩放"。**本文件不采纳计数器**，改为**无状态派生**：

```rust
// db.rs:2060 附近，替换 `if new_file_size >= threshold`
let live = self.live_payload_total().min(new_file_size);
let garbage = new_file_size - live;
let effective = self.options.compaction_threshold_bytes.max(live / 4);
if garbage >= effective { return self.attempt_compaction(); }
```

理由三条：
1. **计数器跨重启清零**，重开一个已积累 50MB 垃圾的 100MB 库后，要再追加 4MB 才压实；派生式不依赖进程内状态，重开即正确。
2. **零新增状态**：Rust 的 `live_payload_total()` 是 O(1) 字段（`live_payload_bytes` 增量账本）；.NET 的 `LivePayloadBytes()` 是 O(命名空间数)，而该调用原本就在死比率分支里每次写都会发生（`Db.cs:1464`）。两条路都无需额外遍历，计数器则要新增字段、在 `append_entries` 递增、在压实成功时归零、并处理压实失败回滚。
3. **悬崖消失是结构性的**：压实后 `garbage ≈ 帧头开销`（28B/帧），远小于 `max(4MB, live/4)`，不可能立即重触发。

**保留**：死比率触发器（`should_compact_by_dead_ratio`）不动 —— 它覆盖"存活坍缩"（清空一个 3MB 库，垃圾 3MB < 4MB 阈值但比率 100%）。`compaction_threshold_bytes = 0` 仍是总开关。

**裁决式验收**（替换原计划的"p99 < 5ms"——小样本 p99 不可靠，且 4MB 垃圾阈值下约每 4000 次写才有 1 次压实，p99 根本采不到）：
- **行为断言（确定性，进 CI）**：6MB 存活、默认阈值下，写入 1000 次（1KB/次，约 1MB 垃圾）后文件大小增长 ≈ 1MB，**不发生全库重写**；继续写到垃圾 ≥4MB 时必须压实一次（用文件大小回落观测）。
- **摊销吞吐（本地基准，`#[ignore]`，不进 CI 门禁）**：6MB 存活稳态 ≥3,000 ops/s（含压实摊销）。CI 里的时间断言会随 runner 抖动，不放门禁。
- .NET 同构 1 个行为断言用例。

**连带修正（并入 FIX-14 的 README 工作）**：README:86 "Deferred 仅提升 15%~31%" 与实测（Immediate ~1,500 → Deferred ~5,000 ops/s，+233%）不符，需按实测重写；规范中的 "68 万 ops/s" 必须标注口径 = **AOL + Manual 批量**（5,000 次写只在内存暂存、结束一次 flush、数据集 640KB），不得作为每写吞吐声明。

**不做**：不为 FIX-21 建 nightly 性能探针（原计划有此一条，与 V2 的"无 nightly 门禁"冲突，删除）。

| 场景 | 现状 | 批次一后 | 说明 |
