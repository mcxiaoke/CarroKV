### 架构调整：写路径拆为「先校验后落盘」两段（三语言同构）

原先三语言的写路径都是 `改内存 → flush → flush 内部才做只读/取锁/磁盘预检`，
导致任何被拒绝的写都会留下「内存已改、调用方却收到错误」的分叉状态。
现将 flush 拆成两个阶段，**所有可预知的拒绝都前移到内存变更之前**：

| 阶段 | Rust | Go | .NET |
| :--- | :--- | :--- | :--- |
| 校验+取锁+§4.1.3 预检（改内存前） | `DbInner::begin_flush() -> (FileLock, u64)` | `DB.beginFlush() (*FileLock, uint64, error)` | `CkvDb.BeginFlush(out ulong)` |
| 序列化 + fsync + 原子轮转 | `DbInner::commit_flush(lock, diskMaxTxId)` | `DB.commitFlush(lock, diskMaxTxID)` | `CkvDb.CommitFlush(lock, diskMaxTxId)` |

涉及的写入口全部改造：`put_*` / `increment_i64` / `delete` / `drop_namespace` /
`clear_namespace` / `batch` / `compact`。锁由 begin 阶段取得、commit 阶段消费
（Rust 靠 `Drop`，Go/.NET 靠 `defer` / `using`），错误路径同样会释放。

### B1（严重，实测确认）：只读实例的写操作污染内存

- 现象：只读实例 `put` 返回 `LockedError`，但随后 `get` 读到新写入的值。
- 根因：`read_only` 校验位于 `flush_snapshot` 内部，即内存变更之后。
- 修复：`read_only` 校验前移到 `begin_flush`，被拒绝的写不再触碰内存。
- 回归测试：`b1_read_only_write_must_not_mutate_memory`（Rust）/ `TestB1ReadOnlyWriteMustNotMutateMemory`（Go）/ `B1_ReadOnlyWriteMustNotMutateMemory`（.NET），覆盖全部 11 个写入口。

### B2（同源）：预检失败不回滚内存

- 现象：`ConcurrentModificationError` / `LockedError` / 磁盘满等 flush 失败后，
  内存保持新值，与调用方看到的错误矛盾。
- 修复：`ConcurrentModificationError` 与 `LockedError` 均改在 `begin_flush`
  抛出，内存未被触碰。真 I/O 失败（磁盘满、rename 重试耗尽）仍发生在内存变更
  之后，语义保持为「内存为权威、下次写入重试落盘」，需在 API 文档显式声明
  （见下方「待文档化」）。
- 回归测试：`b2_external_modification_must_not_mutate_memory`、`b2_locked_must_not_mutate_memory` 及 .NET / Go 同构用例。

### B3：batch 派发「幻影」Watcher 事件

- 现象：batch 内删除不存在的键、清空已空的命名空间、删除已删除的命名空间，
  仍会派发 Delete / Clear / DropNamespace 事件；而单条路径 correctly 不派发。
- 修复：batch 与单条路径语义对齐——**仅当操作实际产生影响时才派发事件**。
- 同步修正：`src/rust/tests/p0_p1_features_test.rs`、`src/go/p0_p1_test.go`
  中原有断言按旧（错误）行为编写，已更新为新语义并补 no-op 断言。
- 回归测试：`b3_batch_must_not_dispatch_phantom_events` 及 .NET / Go 同构用例。

### B4 / B5：.NET 两代轮转非原子

- 现象：`Db.cs` 用 `File.Delete(bakPath)` + `File.Move(db, bak)` 轮转备份，
  中间存在「两代备份同时不存在」的窗口；替换主库用 `Delete` + `Move`，
  失败退化为 `File.Copy` 全量拷贝（非原子）。
- 修复：新增 `AtomicReplace` / `AtomicReplaceWithRetry`——
  - `net8.0`：`File.Move(src, dst, overwrite: true)`
  - `netstandard2.0`：`File.Replace(src, dst, null)`（语义等价的单次系统调用）
  - 带规范 §4.2 的 5/15/30/60/120ms 退避重试；重试耗尽才退化为拷贝兜底
- 回归测试：`B4_BakGenerationMustAlwaysBeThePreviousContent`（行为锁定，防止未来退化）。

### B6：.NET 主库存在时不清理残留 `.db.tmp`

- 现象：`InitAndRecover` 只在主库缺失时检查 `.tmp`；Rust/Go 均无条件处理，
  .NET 会永久遗留垃圾 `.db.tmp`。
- 修复：主库完好时同样安全清理残留 tmp（规范 §4.2 启动自愈第 1 步）。
- 回归测试：`B6_StaleTmpMustBeCleanedWhenPrimaryExists`。

### 待文档化（本轮未改，建议 API 文档补上）

1. **真 I/O 失败的语义**：磁盘满 / rename 重试耗尽发生在内存变更之后，
   此时内存为权威状态，下次写入会重试落盘；若进程不再写入则退出时丢失。
   调用方不应假设「写失败 = 什么都没发生」。
2. **`lockTimeoutMs` 的双重语义**：它既是本进程的等待上限，也是判定锁僵死的
   年龄阈值（`now - CreateTimeMs >= lockTimeoutMs`，与 Go/Rust 一致）。
   因此**大于 `lockTimeoutMs` 的写操作会被其他进程判为僵死并尝试窃取**；
   大库写入时应相应调大该值。
3. **锁为每次 flush 级**：`.lock` 在每次 flush 时获取/释放，并非会话级持有；
   多进程并发读写同一个数据库文件明确不支持（规范 §1.1）。
