### 条目 3 — Go Windows 共享冲突判定（P0-3）
- `isWindowsSharingViolation` 由比较 `syscall.EACCES/EBUSY/ETXTBSY` 改为比较**裸 Win32 码**
  `5 / 32 / 33`。Go 把 `syscall.E*` 定义在 `APPLICATION_ERROR + n` 的合成区间
  （EACCES=536870913 / EBUSY=536870928 / ETXTBSY=536871035），与操作系统真实传回的
  5/32/33 分处完全不同的数值区间，谓词**恒为 false**，规范 §4.2 要求的
  `[5,15,30,60,120]ms` 共 230ms 退避一次都没执行过。
- Win32 裸码常量上移到无 build tag 的 `errors.go` 供跨平台判定复用，
  `lock_windows.go` 改为引用同一份定义（原先两处重复定义）。

### 条目 4 — `.tmp` 晋升失败必须让 `Open` 失败（P1-19）
- **Go**：`renameWithRetry` 的错误不再被 `_ =` 丢弃，晋升失败返回 `IoError` 并在消息中给出
  `.tmp` 位置。修前 `Open` 会**静默成功返回空库**，而唯一完好的数据还躺在 `.tmp` 里。
- **Kotlin**：`File.renameTo` 的返回值不再被忽略；晋升失败抛 `CorruptedError` 并保留 `.tmp`。
  同时把"内容确实不可解析（可安全删除 `.tmp`）"与"晋升失败（必须保留）"两类失败拆开。
- **.NET / Dart（超出评审清单的同类修复）**：原实现的 catch-all 会把**已校验通过**的 `.tmp`
  一并删除——即销毁唯一的好数据，还把一次瞬时 IO 失败伪装成"内容确实损坏"。
  现两类失败分开处理，晋升失败时保留 `.tmp` 并让 `Open` 失败。

### 条目 5 — Kotlin 写入口收口（P1-26）
- 新增 `private inline fun <T> writeLocked(action)`：先 `checkWritable()` 再取写锁。
  `applyMutation` / `incrementInt64` / `dropNamespace` / `batch` 的提交块统一改走它。
- 修前 `incrementInt64` 与 `dropNamespace` 直接 `rwLock.write`，在 `readOnly = true` 下：
  AOL 引擎会**真的**往 `.db` 追加帧并 fsync；SNAPSHOT + Immediate 会先 `getOrPut` 塞入空 store、
  之后才抛 `LockedError`，失败却在 `namespaces()` 里留下幽灵命名空间。
- 顺带修：两处提交块此前漏了 `dirtyGeneration++`（`applyMutation` 有、这两个没有）。

### 条目 6 — 加载期校验 `NsLen ≤ 255`（P1-3）
- Rust / .NET / Go / Dart 的条目解码处补 `ns_len > 255 → CorruptedError`（Kotlin 此前已有）。
- 修前 `ns_len`（uint16，可达 65535）不做任何上限校验，超长命名空间会被加载并常驻内存、
  出现在 `namespaces()` 中，却被 `get_*`/`put_*`/`delete`/**`drop_namespace`**/**`clear_namespace`**
  全部以 `InvalidNamespaceError` 拒绝——**既读不出也删不掉**，且每次快照都把它重新序列化进
  `.db` / `.bak` / 全部 `backup()` 产物，污染其余四门语言。

### 条目 7/8 — .NET 注册表与 `Open` 失败路径（P0-5 / P0-6）
- `Open` 的 `while (true)` 改为**有迭代上限**的 `for`，任何 `TryAdd` 之前先按 (key, value)
  原子驱逐死弱引用条目。修前实例被 GC 回收但未 `Dispose` 时，`ConcurrentDictionary.TryAdd`
  因 key 已存在**必然失败** → 每轮重新 `new` + `LockFile.Acquire` + `InitAndRecover`
  （全量读盘校验）→ `continue` → **进程硬挂死 + 无限磁盘 IO**，每个泄漏的 `FileStream` 无界增长。
- `InitAndRecover` 失败（最常见是 `CorruptedError`）时 `Dispose` 掉半成品实例，释放跨进程
  连接锁。修前用户按提示"修好 `.db` 后重开"，接下来 10 秒却拿到 `LockedError` 而非
  `CorruptedError`——错误信息把排查引向"别人在用"。
- 顺带修：`Open` 输掉注册竞争的每条路径（`TryUpdate` 失败后 `continue`、`TryAdd` 失败但条目
  已消失、返回竞态实例）此前都直接丢弃已取到锁的临时实例，每命中一次泄漏一个内核锁句柄。
  新增 `DisposeLoserInstance` 统一回收。

### 条目 9 — Dart `Timer` 泄漏（P1-23）
- 定时器创建从构造函数移到 `_initAndRecover()` 成功之后的 `_startSyncTimer()`；

- 修前 `SyncMode.deferred` 下的**任何** `open()` 失败（目录不存在、库损坏、`LockedError`）
  都让 `Timer.periodic` 挂住 Dart VM 事件循环，进程永不退出——CLI 工具直接挂死。

### 条目 10 — .NET `Snapshot.Release` 原子化（P1-17）
- 非原子的 `if (_isDisposed) return; _isDisposed = true;` 改为 `Interlocked.Exchange` 一次性闩锁。
  两线程并发 `Dispose` 会双双通过检查 → `ReleaseSnapshot()` 被调两次 → `_snapshotCount` 提前归零
  → 后续写路径的 `if (_snapshotCount > 0)` 全为假 → 原地修改 `NamespaceStore.Items` →
  **仍然存活的 Snapshot 正在读的列表被就地改写**，快照隔离被打破、返回撕裂数据。

### 条目 11 — ReadOnly 配置冲突改抛错（P1-15 / P1-38）

- **语义**：单例语义下命中注册表的 `open()` 必须原样返回既有实例，因此无法满足不同的
  `ReadOnly` 请求。以 `ReadOnly = true` 打开却静默拿到读写实例 = **静默提权**
  （且 `onWarning` 默认 null 时连告警都看不见）；反方向会让后续写入在远处以
  `LockedError` 失败、误导排查。两个方向都拒绝。
- `EngineMode` / `SyncMode` 冲突**维持告警**：只造成性能与落盘语义差异，不构成权限问题。

  Rust/.NET/Go 的 `backup` / 只读备份用例原先在读写实例存活时以只读重开同路径，
  已改为先释放读写单例。`WriteAtomicityRegressionTest.B1` 同理。

## 2026-10-17 14:22:37 — 其余三种语言同步修复（Go / Kotlin / Dart）

### FIX-21 压实悬崖（Go / Kotlin / Dart）

三处触发条件都是 `newFileSize >= compactionThresholdBytes`，改法一致：
`garbage = fileSize − livePayload`，`garbage >= max(threshold, live/4)`。

- `src/go/db.go`（`maybeCompactAfterWrite`）
- `src/kotlin/src/main/kotlin/ckv/CkvDb.kt`（`maybeCompactAfterWrite`）

- 垃圾率恒为 100% → 死键比例触发器**每次写都压实**；

## 2026-10-17 15:58:22 — 关闭后写守卫（FIX-22，五语言）+ 规模实测

### FIX-22 `close()` 之后禁止写入

**根因**：`close()` / `Dispose()` 按要求释放跨进程连接锁（C9/FIX-02c），但释放之后句柄仍可写。此时写入会落到一个可能已被另一个进程打开的库上——正是锁要阻止的双写者场景。

**实测证据（修复前）**：
- Go：`Close()` 后 `PutString` 返回 `err=<nil>`；
- Dart：`close()` 后 `putString` 静默成功；
- .NET：写路径没有 disposed 检查，只有 `_rwLock` 被 Dispose 后才偶然抛 `ObjectDisposedException`（语义不是 `Locked`）；
- Kotlin：会抛，但类型是通用 `CkvException`，与 Rust/契约的 `Locked` 不一致。

**修复**：
- Go `DB.closed`：`applyMutation`/`Flush`/`Compact` 返回 `NewLockedError`；`Close` 幂等。
- Dart `_checkWritable()`：`_applyMutation`/`flush`/`compact` 抛 `LockedError`。
- .NET `ThrowIfDisposed()`：`ApplyMutation` + 6 个写入口（Put/Delete/Drop/Clear/Batch/Increment）在取写锁前检查，抛 `LockedError`（`DatabaseLockedException`）。
- Kotlin `checkDisposed()` 改为抛 `LockedError`。
- 契约写入 `docs/API-V1-FREEZE.md §3.16`：关闭后写/刷盘/压实必须失败，读不强制失败但只反映内存快照，`close()` 幂等。

**测试**：`src/go/closed_handle_test.go`、`src/dart/test/closed_handle_test.dart`、`src/dotnet/tests/Ckv.Tests/ClosedHandleTest.cs`、`src/kotlin/.../ClosedHandleTest.kt`。断言包含"被拒绝的写不得修改文件"。

> 更正：本人上一轮称 ".NET/Kotlin 已有守卫"，实测表明 .NET 的 `_isDisposed` 只在后台刷盘与注册表路径使用，写路径并未接入；Kotlin 的错误类型也不符合契约。两处均已修正。
