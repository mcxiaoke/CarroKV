### FIX-21 AOL 压实阈值悬崖（Rust + .NET + 规范）

- **根因**：`maybe_compact_after_write` 以"文件绝对大小 ≥ 阈值"触发，而压实后文件恰等于存活大小 → 存活数据 ≥4MB 后每次写都全库重写。实测 6MB 存活 26.1ms/写（38 ops/s）、20MB 86.0ms/写（12 ops/s），对照（关闭压实）0.2ms。
- **修法**：改为 `garbage >= max(threshold, live/4)`，`garbage = fileSize − live`。**不引入**原计划的 `bytes_appended_since_compaction` 计数器：派生式无需新增状态、重开库后依然正确（计数器会清零），且 `live_payload_bytes` 本就是 O(1) 账本。
- 文件：`src/rust/src/db.rs`（`maybe_compact_after_write`）、`src/dotnet/src/Ckv/Db.cs`（`MaybeCompactAfterWrite`）、`docs/KV-DB-DESIGN-SPEC.md` §4.5。
- 测试：`src/rust/tests/wal_threshold_cliff_test.rs`、`src/dotnet/tests/Ckv.Tests/WalThresholdCliffTest.cs`（行为断言，无时间阈值）。红验证：移除修复后两个断言均失败，且耗时从 2.4s 膨胀到 113s。

### FIX-01 后台刷盘竞态（Rust + .NET）

- **根因**：`bg_flush_step` 在锁外写共享 `<db>.tmp`，与显式 `flush()` 并发；且轮转前不校验代际，陈旧快照可覆盖已确认写入并误清 `is_dirty`。
- **修法**：`DbInner` 增加 `flush_mutex: Arc<Mutex<()>>` 与 `dirty_generation: u64`（.NET：`SemaphoreSlim(1,1)` + `_dirtyGeneration`）。所有 `.tmp` 生产者互斥；bg 轮转前校验代际，不一致则删除 `.tmp` 并保留脏标记。锁序恒为 `flush_mutex → RwLock`；AOL 路径不取 flush_mutex（只 fsync），避免循环等待。
- 文件：`src/rust/src/db.rs`（`bg_flush_step` / `flush` / `close` / `compact` / `apply_mutation`）、`src/dotnet/src/Ckv/Db.cs`（`FlushIfDirty` / `Flush` / `Compact` / `Dispose` / `ApplyMutation`）。
- 测试：`src/rust/tests/deferred_flush_race_test.rs`、`src/dotnet/tests/Ckv.Tests/DeferredFlushRaceTest.cs`。
- **实证**：仅移除代际校验（保留互斥）时测试仍失败 → 证明"只加互斥不够"，两道保护都是必需的。

### FIX-02 跨进程锁语义（Rust，仅 a/c；.NET 共享模式不动）

- **修法**：(a) `FileLock::acquire` 把 `open(<db>.lock)` 纳入退避循环，Windows `{5,32,33}` 与 `WouldBlock` 视为竞争，超时后返回 `DbError::Locked`（此前 .NET 持 `FileShare.None` 时 Rust 立即 `IoError`，`lock_timeout_ms` 被绕过）；(c) `close()` 显式释放内核锁，并置 `closed=true`、从同进程注册表移除。
- **保留 `FileShare.None`**：规范 §1.1 明确不支持多进程并发读写，锁的职责是快速失败；放开共享会把 .NET 的强制互斥降级为 advisory。
- 文件：`src/rust/src/lock.rs`、`src/rust/src/db.rs`（`close`、`check_writable`、`closed` 字段）。
- 测试：`src/rust/tests/lock_close_release_test.rs`（close 后外部可加锁、重开 <500ms、Windows 共享冲突→`Locked` 且耗时≥150ms）。

## 2026-10-17 14:22:37 — 其余三种语言同步修复（Go / Kotlin / Dart）

批次一原先只改了 Rust 与 .NET。逐个核对后确认：**同样的缺陷确实存在于其余三种语言**，且顺带挖出两个更严重的潜伏 bug。

### FIX-21 压实悬崖（Go / Kotlin / Dart）

三处触发条件都是 `newFileSize >= compactionThresholdBytes`，改法一致：
`garbage = fileSize − livePayload`，`garbage >= max(threshold, live/4)`。

- `src/go/db.go`（`maybeCompactAfterWrite`）
- `src/kotlin/src/main/kotlin/ckv/CkvDb.kt`（`maybeCompactAfterWrite`）
- `src/dart/lib/src/db.dart`（`_maybeCompactAfterWrite`）

**同时发现（比悬崖更严重的潜伏缺陷）**：Go 与 Dart 的装载快路径直接 `append` 到 `items`，绕过了维护 `liveBytes` 的 `put()`，导致**重开任何 ≥2MB 的 AOL 库后存活账本为 0**：
- 垃圾率恒为 100% → 死键比例触发器**每次写都压实**；
- 与 FIX-21 叠加后，每次写都走全库重写。
实测证据：修复前 Go 的 `garbage past the threshold` 用例耗时 92s、Dart 用时 2m03s；修复后分别 4.6s / 7s。修复方式是装载后重算一次账本（`recalculateLiveBytes()`），与规范 §4.5「绕过 put/delete 的批量装载路径必须重算」一致。Kotlin 的装载走 `put()`，不受影响。

回归测试：`src/go/wal_threshold_cliff_test.go`、`src/kotlin/.../CompactionThresholdCliffTest.kt`、`src/dart/test/wal_threshold_cliff_test.dart`。

### FIX-01 后台刷盘竞态（Go / Kotlin）

- **Go**：`DB` 增加 `flushMu sync.Mutex` + `dirtyGeneration uint64`；`flushIfDirty` 在 SnapshotAtomic 下持门，轮转前校验代际；`Flush`/`Compact`/`Close` 先过门；`Close` 重构为「停止后台 → join → 过门 → 最终刷盘」。
- **Kotlin**：`CkvDb` 增加 `flushGate: ReentrantLock` + `dirtyGeneration`；`flushIfDirty` 拆出 `flushIfDirtyLocked` 并由 `flushGate` 保护（AOL 不取门）；`flush`/`compact`/`close` 过门。`close()` 改为**在锁外等待 executor 结束**——旧实现在持有 `rwLock.write` 时 `awaitTermination(1s)`，工作线程若正等写锁就自锁，只能靠超时"解开"并可能提前返回。
- **Dart 不适用并已确认原因**：单 isolate + 同步文件 IO，`Timer` 回调无法与显式 `flush()` 交错（其后台回调本身就只是 `flush()`）。
- 红验证：Go 去掉代际校验即丢写；Kotlin 去掉互斥即丢写（其 `flush()` 没有"不脏就返回"的短路，代际校验在 Kotlin 中是冗余但保留以统一语义）。

### FIX-06 / FIX-07（Go / Kotlin / Dart）

- FIX-06：最终刷盘失败不再静默吞掉——Go 通过 `OnWarning("onFinalFlushFailed")` 上报并把错误返回给 `Close()`；Kotlin/Dart 通过 `onWarning` 上报。

## 2026-10-17 15:58:22 — 关闭后写守卫（FIX-22，五语言）+ 规模实测

### FIX-22 `close()` 之后禁止写入

**根因**：`close()` / `Dispose()` 按要求释放跨进程连接锁（C9/FIX-02c），但释放之后句柄仍可写。此时写入会落到一个可能已被另一个进程打开的库上——正是锁要阻止的双写者场景。

**实测证据（修复前）**：
- Go：`Close()` 后 `PutString` 返回 `err=<nil>`；
- Dart：`close()` 后 `putString` 静默成功；
- .NET：写路径没有 disposed 检查，只有 `_rwLock` 被 Dispose 后才偶然抛 `ObjectDisposedException`（语义不是 `Locked`）；
- Kotlin：会抛，但类型是通用 `CkvException`，与 Rust/契约的 `Locked` 不一致。

**修复**：
- Go `DB.closed`：`applyMutation`/`Flush`/`Compact` 返回 `NewLockedError`；`Close` 幂等。
- Dart `_checkWritable()`：`_applyMutation`/`flush`/`compact` 抛 `LockedError`。
- .NET `ThrowIfDisposed()`：`ApplyMutation` + 6 个写入口（Put/Delete/Drop/Clear/Batch/Increment）在取写锁前检查，抛 `LockedError`（`DatabaseLockedException`）。
- Kotlin `checkDisposed()` 改为抛 `LockedError`。
- 契约写入 `docs/API-V1-FREEZE.md §3.16`：关闭后写/刷盘/压实必须失败，读不强制失败但只反映内存快照，`close()` 幂等。

**测试**：`src/go/closed_handle_test.go`、`src/dart/test/closed_handle_test.dart`、`src/dotnet/tests/Ckv.Tests/ClosedHandleTest.cs`、`src/kotlin/.../ClosedHandleTest.kt`。断言包含"被拒绝的写不得修改文件"。

> 更正：本人上一轮称 ".NET/Kotlin 已有守卫"，实测表明 .NET 的 `_isDisposed` 只在后台刷盘与注册表路径使用，写路径并未接入；Kotlin 的错误类型也不符合契约。两处均已修正。
