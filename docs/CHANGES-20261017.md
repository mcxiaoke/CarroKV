## 11:57:15 — 写路径收敛落地（五语言）+ 修复 Go `Close()` 停等竞态

**背景**：RC2 归因（见上一条与 [RC2 报告](RC2-WAL-FIXED-OVERHEAD-ATTRIBUTION-20261017.md)）查明单次写的固定开销中，`fsync` 之外还有 **3 次路径 `stat`（其中 2 次纯冗余）+ 1 次 `create` 判定 + 2 次句柄元数据**。本轮把这四项收敛掉，不改磁盘格式、不改 API、不动句柄生命周期（不触碰 C15）。

### 写路径改动（Rust / Go / .NET / Kotlin / Dart）

| 语言 | 改动 |
| :--- | :--- |
| Rust | `precheck_disk_state` 单次 `metadata()`（NotFound ⇒ `(0,0)`）；`append_entries` 删除 `path.exists()`，空文件由 `seek(End)` 判定；`open` 去掉 `create` 标志、NotFound 回退；`new_file_size` 用 `stream_position()` 取代 `metadata()` |
| Go | `appendEntries` 删除重复 `os.Stat`；`O_CREATE` 移到 `IsNotExist` 回退分支；`f.Stat()` 改为 `Seek(0, io.SeekEnd)` |
| .NET | `ProbeDiskState` 用单个 `FileInfo`（`Exists` 已缓存）取代 `File.Exists + new FileInfo`；`AppendEntries` 新增 `OpenLogFile()`（`FileMode.Open` + NotFound 回退）；空文件由 `Seek(End)` 判定；`fs.Length` → `fs.Position` |
| Kotlin | `precheckDiskState` 单次 `Files.readAttributes`；`appendEntries` 合并两次 `FileOutputStream` 为一次、删除 `exists()`、`length()` → `channel.size()`；`mkdirs` 收进 `FileNotFoundException` 分支 |
| Dart | `_precheckDiskState` 单次 `statSync()`；`_appendEntries` 删除 `existsSync()` |

Kotlin 的 `O_CREAT` 未能去掉：`FileOutputStream(…, true)` 恒定带 `O_CREAT`，改写需换 `FileChannel.open(WRITE, APPEND)` 并替换 `fd.sync()`，留作独立重构。

### A/B 实测（同机同负载，3 轮中位数，基线为 HEAD 单独编译的二进制）

| 卷 | 模式 | 改动前 | 改动后 | 加速 |
| :--- | :--- | ---: | ---: | ---: |
| C: NVMe | WAL + Immediate | 951.5 µs | 628.8 µs | **1.51x** |
| C: NVMe | WAL + Manual | 420.3 µs | 165.9 µs | **2.53x** |
| F: NVMe | WAL + Immediate | 1,402.0 µs | 1,268.0 µs | 1.11x |
| F: NVMe | WAL + Manual | 305.2 µs | 134.3 µs | **2.27x** |

`Manual` 不含 `fsync`，是纯系统调用节省（2.3–2.5x）；`Immediate` 随该介质 `fsync` 占比升高而稀释（F 卷 fsync 约占 82%）。

### 修复 Go `Close()` 停等竞态（存量缺陷）

**现象**：Linux 单核上全量测试挂死 6 分钟以上，`ckv.test` 处于 0% CPU 阻塞态。

**根因**：后台刷盘 goroutine 每轮重新读取 `db.stopCh` 字段，而 `Close()` 是 `close(stopCh)` → `db.stopCh = nil` → `bgWg.Wait()`。若 goroutine 在字段置 nil 之后才第一次求值 `select`，就 select 到 **nil channel**，等满 `syncInterval`（测试设为 1 小时）。

**修复**：`go` 语句处按值捕获通道，goroutine 不再读字段。与今日 11:10 修复的 Rust C16（`wait_for` 前未检查关闭标志）属同一族缺陷。

**回归用例**：`TestDeferredCloseDoesNotWaitForTheSyncInterval`（1 小时周期 + 5s 上限）。已反向验证：远端改回 `<-db.stopCh` 后该用例 5.00s 失败，恢复后 0.01s 通过；Windows 多核无法复现，缺陷只在单核稳定暴露。

**测试**：Rust 全绿（1 既有 ignore）、Go 全绿、.NET 99、Kotlin 59、Dart 55；Go 在 Linux 单核（源码在 `/data`）全绿 10.4s。

## 11:31:29 — RC2：WAL 写路径固定开销归因（X-1 实验完成，纯诊断）

**产出**：[RC2-WAL-FIXED-OVERHEAD-ATTRIBUTION-20261017.md](RC2-WAL-FIXED-OVERHEAD-ATTRIBUTION-20261017.md)；实验程序 `temp/rc2-attribution/`（未改 `src/` 任何代码）。

**归因结论**（C 卷，三因子交替实验，三轮取中位数）：

| 成本项 | 均值 | 占比 |
| :--- | ---: | ---: |
| `fsync` | 459 µs | 53% |
| 前置 `stat`（3 次，其中 2 次冗余） | 226 µs | 26% |
| 每写 `open`+`close` | 195 µs | 23% |
| 纯写 160B | 3.5 µs | 0.4% |

- 微基准与库端到端偏差 0.02%~1.0%，模型可解释 95% 以上成本。
- **历史数据不可复现**：本次 `WAL+Immediate` 855.8 µs（1,169 ops/s），2026-10-16 报告为 2.24 ms（446 ops/s），差 2.6 倍。
- **`fsync` 占比非结构常量**：同机 C 卷 0.44 ms / D 卷 38.7 ms，差 77 倍。
- **C15 证据链失效**：原依据"fsync 仅占 15–31%"不成立（本次 54%）；组提交维持搁置，但理由改为结构性——单写者无批次可合。
- **零风险优化候选**：前置 stat 3→1（−17.4%）、去 `create` 标志（−8.7%）、去两次 handle metadata（≤2%），叠加 864.8 → 637.8 µs（**1.36x**），不动格式/API/句柄生命周期。五语言均有同款冗余（Kotlin 达 4 次 stat）。
- **口径修正**：库未发布，"磁盘格式冻结"名不副实；格式改动的成本是五语言同步改 + 向量重生成的工作量，不是禁忌。但压缩的黄金向量双层化仍必要——Deflate 输出字节本身不确定，`SHA-256 相等`判据物理上不成立。

## 11:10:20 — 修复 Rust Deferred 模式下 `close()` 可能阻塞整个刷盘周期（C16 握手缺陷）

**发现路径**：批次 3 的自适应压实测试把 `sync_interval_ms` 设为 1 小时以隔离后台刷盘，全量并行运行时该用例稳定挂起 20 分钟以上；单独运行却始终 0.3s 通过。

**根因**：后台刷盘线程的等待顺序是"先 `wait_for`，后检查关闭标志"。`Drop` 先置标志再 `notify_all`；若通知恰好落在工作线程两次 `wait_for` 之间（例如正在执行 `bg_flush_step`），唤醒丢失，`join()` 要等满整个 `sync_interval_ms`。默认 100ms 掩盖了该缺陷，调大周期即暴露。

**修复**：进入 `wait_for` 之前先检查一次关闭标志（双重检查），并在唤醒后再检查一次。

**测试**：新增 `test_deferred_close_does_not_wait_for_the_sync_interval`（1 小时周期下 `drop` 必须 5s 内返回）。Rust 全量 101 passed，耗时从 2 分钟级降到 18s。

## 10:51:33 — 批次 4：批内"读已写"（RC1，五语言）

**背景**：`BatchWriter` 只有写方法，批次回调内无法读取自己刚写入的值，也无法基于已有数据做条件分支；Rust 的 `batch(FnOnce(&mut Batch))` 闭包拿不到数据库句柄。库尚未发布，允许破坏性签名调整。

**语义（五语言逐条对齐，写入规范 §5.2.2 与 API v1.1 §3.18）**：

1. 暂存区优先：从后向前扫描，最近一次操作生效；
2. 墓碑遮蔽：暂存 `delete` / `drop_namespace` / `clear_namespace` 命中的键一律视为"不存在"，即使主库仍有该值；
3. 回落已提交状态：本批次未触碰的键读主库当前状态（读锁内读取），批次期间其他线程的提交对未触碰键可见；需要冻结视图请先 `snapshot()`；
4. 类型/编码校验与 `Get*` 一致：`GetString` 对非字符串值抛 `TypeMismatchError`，非法 UTF-8 抛 `InvalidUtf8Error`。

**代码变更**

| 语言 | 变更 |
| :--- | :--- |
| Rust | `Batch` 增加 `db: Option<Arc<RwLock<DbInner>>>` 与 `get_bytes`/`get_string`；`batch()` 注入句柄；`Batch::new()` 保留"仅暂存"语义；`Debug` 改为手写实现 |
| Go | `BatchWriter.GetBytes` / `GetString`：反向扫描 `ops`，回落在 `db.mu.RLock()` 内走 `namespaces` |
| .NET | `BatchWriter.GetBytes` / `GetString`：反向扫描 `Ops`，回落到 `CkvDb.GetBytes/GetString`（复用其类型校验） |
| Kotlin | `BatchWriter(db)` 持有数据库引用，新增 `getBytes` / `getString`；`batch()` 传入 `this` |
| Dart | `BatchWriter` 增加 `readBytes` / `readString` 回调（避免 storage↔db 循环依赖），`batch()` 注入 `CkvDb.getBytes/getString` |

**测试**：新增 16 个用例（Rust 5、Go 3、.NET 3、Kotlin 4、Dart 4，均覆盖暂存命中、墓碑遮蔽、回落已提交、WAL 模式、类型校验）。Dart 55、Kotlin 59、.NET 99、Go 全通过、Rust 全通过。

### RA2 自适应压实（五语言）

- **新增死键比例触发器**：`fileSize >= 2 MB` 且死数据占比 `>= 50%` 时压实，与原有 `compactionThresholdBytes` 触发器并列；`threshold == 0` 仍关闭全部自动压实。
- **O(1) 增量账本**：`livePayloadBytes = Σ(len(key)+len(value))`。Rust 在 `DbInner::mem_put/mem_delete/mem_drop/mem_clear` 统一收口（同时把 8 处分散的内存变更闭包收敛到这四个方法，并让 `apply_entries` 装载路径同样记账）；Go/Kotlin/Dart/.NET 在 `NamespaceStore.put/delete` 内记账，`.NET` 的批量快速装载路径额外调用 `RecalculateLiveBytes()`。
- 复用现有 `maybeCompactAfterWrite` 的退避/失败计数体系（D2 契约不变，不新增公开选项）。

**测试**：新增 15 个用例（每语言 3 个：比例触发、2 MB 基线、零阈值总开关）。Dart 51、Go 全通过、Kotlin 55、.NET 96、Rust 全通过。

## 10:22:42 — 批次 1：默认值可靠性优先与 Dart 默认值对齐（RA3 / RA4）

**背景**：2026-10-16 的缺口评审确认 Dart 三处默认值（`lockTimeoutMs` 5000、`syncIntervalMs` 50、`compactionThresholdBytes` 0）落后于其余四语言（C8/C19 欠账）。其中 `compactionThresholdBytes = 0` 会**关闭 Dart 的 WAL 自动压实**，属行为级漂移而非数值差异。
