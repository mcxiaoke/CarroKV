## 三、P0 阻塞项（不修不能冻结 API）

### P0-1（新·实证）：Rust `Db::get_*` 全线缺失 `TypeMismatchError` 拦截

- 规范 §5.2.2 明确要求 `getString/getInt64/getFloat64/GetBool` 在 `ValueType` 不匹配时抛 `TypeMismatchError`。
- 实证（Rust）：
  ```
  RUST get_string(int64) => Ok(Some("*\0\0\0\0\0\0\0"))   // 42 的 8 原始字节被当 UTF-8 解码！
  RUST get_i64(string)  => Err(Corrupted("Expected 8 bytes for i64, got 5"))  // 错误类型也错
  ```
- 对照：Go / .NET 均正确抛 `TypeMismatchError` / `TypeMismatchException`（实证确认）。**Rust 是三语言中唯一违背的**。
- 加重情节：Rust 的 `Snapshot::get_string`（db.rs:875）**有**类型检查，而 `Db::get_string`（db.rs:170）没有——同一文件内自相矛盾，明显是遗漏而非设计。
- 修复：`Db::get_string/get_i64/get_f64/get_bool` 四个方法补 `value_type` 校验，与 Snapshot 实现对齐；`Entry::as_*`（types.rs）同样缺失检查，一并补。

### P0-2（新·实证）：.NET 加载器静默忽略 `OpDelete` / `OpDropNamespace`

- 规范 §3.3.4：重放 BatchFrame 必须按序应用全部三种 OpCode。
- 实证（.NET，手工构造含 OpDelete 的合法文件）：
  ```
  DOTNET load file with OpDelete => OPENED (count=1) - should apply delete (expect 0 if handled)
  ```
- Rust / Go 均正确应用删除。.NET `LoadFromBytes`（Db.cs:293-328）只处理 `opType == OpPut`。
- 影响：阶段一快照文件不含删除 op 所以现有 interop 测试暴露不了；但规范违背 + 跨语言读取含墓碑的文件行为分叉。阶段二启用追加写后此问题将直接导致数据错误。

### P0-3（新·实证）：.NET 加载器不校验 TxID 单调性

- 规范 §3.4：加载时验证 `TxID > lastTxID`，否则判定损坏。
- 实证（.NET，构造 TxID=5 后接 TxID=3 的合法 CRC 文件）：
  ```
  DOTNET load non-monotonic TxID file => OPENED (count=2) - spec violation if no error
  ```
- Rust / Go 均正确拒绝（`Non-monotonic TxID` CorruptedError）。
- 同类缺失：.NET 也不校验 `OpCount` 的 `1 <= n <= 1,000,000` 范围（Rust/Go 均校验）。

### P0-4（第一轮 B1·本文复现实证）：清空后同实例再写自触发 `ConcurrentModificationError`

- 实证（Go）：
  ```
  GO B1: clear-then-write on same instance => err=ConcurrentModificationError: Disk state changed externally: expected (1, 32), found (0, 32)
  ```
- 根因（与第一轮分析一致，本文确认代码路径）：清空后磁盘落 32B 空文件，`scan_max_tx_id` 对空文件返回 0，与内存 `last_known=(1,32)` 比较误判外部修改。
- Rust `flush_snapshot`（db.rs:1117-1137）同款逻辑，同样触发。
- 这是**普通用户必然踩到**的崩溃路径（`clear → 再写`），且现有测试全部未覆盖（测试都是 clear 后 close/reopen）。

### P0-5（第一轮 A1·本文补充）：`KeyChangeOp` 三语言三种形态

- 规范 §5.2.3：`Put=1, Delete=2, DropNamespace=3, Clear=4`。
- 现状：
  - Rust：enum 仅 `Put, Delete` 两变体，`drop/clear` 发逐键 `Delete` 事件（实证：watcher 收到 4 条 Delete）；
  - Go：仅 `OpChangePut, OpChangeDelete`，且 **iota 从 0 开始（Put=0, Delete=1）**，数值与规范的 1/2/3/4 也不一致（实证输出 `[0 1 0 1]`）；
  - .NET：`Put=1, Delete=2, DropNamespace=3, Clear=4` ✓（实证 `[Put, Clear, Put, DropNamespace]`）。
- 后果：订阅者无法区分删键/删空间/清空；Go 的事件数值序列化后与另两种语言错位；Rust/Go 的 batch drop/clear 同样只发 Delete。
- 修复：Rust/Go 补齐 4 元枚举并**按规范数值定义**（Go 需显式赋值而非 iota），drop/clear/batch 路径发正确 op。

### P0-6（第一轮 A2·本文复现）：`delete` / `drop_namespace` / `clear_namespace` 返回值不一致

- 规范：均返回 `bool`（是否实际命中）。
- 实证：
  ```
  RUST  delete(existing) => Ok(()), delete(missing) => Ok(())          // 无 bool
  GO    Delete(existing)=<nil> Delete(missing)=<nil>                    // 无 bool
  DOTNET Delete(existing) => True, Delete(missing) => False             // ✓
  ```
- Rust 内部已算出 `existed` 却丢弃（db.rs:367-378）。
- 修复：Rust `Result<bool>`、Go `(bool, error)`。

### P0-7（第一轮 A3）：`batch.clear_namespace` 在 Rust/Go 缺失

- .NET `BatchWriter.ClearNamespace` ✓；Rust `BatchOp` 无此变体、Go `BatchWriter` 无此方法。
- README 核心功能一节明确宣传了该 API，属于文档承诺未兑现。

### P0-8（第一轮 A4·本文代码复核确认）：.NET 锁文件 32B 布局偏离规范 4 字节

- 规范 §4.1.2：`0..8 PID(uint64) | 8..24 LockUUID | 24..32 CreateTimeMs`。Rust/Go 符合。
- .NET `LockFile.cs:34-37`：`0..4 PID(uint32) | 4..20 UUID | 20..28 CreateTimeMs`，整体偏移 4B，且 PID 用 uint32。
- 后果：.NET 写的锁文件被 Rust/Go 误读（时间戳读成 0 退回 mtime、UUID 比对区间错位永不删除）；v3.2 把此布局列为硬性锁定决策，公开发布前必须对齐。

## 四、P1 重要项（冻结前应修复）

### P1-1（新）：.NET `DbOptions` 缺 `ForceUnlock` 与 `OnWarning`（实证确认）

- 实证：`DOTNET DbOptions has ForceUnlock? False, OnWarning? False`。
- 规范 §5.1.1 两者均为必选字段；Rust/Go 都有（Go 的 `OnWarning` 存在但 .NET 用 `AutoRecoverFromBackup`（bool）替代，语义不对等——恢复告警无法通知调用方）。

### P1-2（新）：.NET 缺 `Compact()`（实证确认）

- 实证：`DOTNET has Compact()? False`。规范 §5.2.2 列出 `compact()`；Rust/Go 均有。

### P1-3（第一轮 A5·本文补充 TxID 部分）：.NET `FlushSnapshot` 无 §4.1.3 磁盘预检，且 TxID 不感知磁盘

- .NET 完全没有 `last_known_disk_state` 机制，不会抛 `ConcurrentModificationError`。
- 且 `nextTxId = _currentMaxTxId + 1`（Db.cs:372），未按规范 §3.2.1 取 `max(memoryKnownMaxTxID, diskScannedMaxTxID) + 1`——外部进程改过磁盘时会写倒退的 TxID，产生 Rust/Go 会拒绝加载的文件。

### P1-4（新·实证）：Go/.NET 冷启动加载 O(N²)，Go 实测 5 万条 35 秒

- `namespaceStore.put`（Go）每次插入 `copy(items[idx+1:], items[idx:])` 是 O(n) memmove；.NET `List.Insert` 同理。按序加载 N 条 = O(N²)。
- 实证（本机，Go，5 万条）：`cold open 50000 entries took 34.99s`。Rust 用 BTreeMap 是 O(N log N)，同数据量亚秒级。
- 磁盘快照本身已按规范排好序（§3.3.2），加载器本可顺序 append 做到 O(N)。
- 该问题直接打击 benchmark 报告里"50k 条冷启动 76 秒（单核 Linux）"的极端数字，也是移动端体验的硬伤。
- 修复：加载路径改为 append 全部后一次性排序（或检测已有序直接 append）；Go/.NET 同步。

### P1-5（新）：Go/.NET 写路径无条件全量 clone 命名空间（Rust 无此问题）

- Go `putInternal`（db.go:800-811）与 .NET `GetOrCreateStoreForWrite`（Db.cs:665-676）在**没有任何快照存在时**也每次 clone 整个 namespace item 切片，O(n) 内存拷贝 + GC 压力。
- Rust 的 `Arc::make_mut` 在引用计数为 1 时是 O(1) 原地修改。
- Go batch 内 k 个 delete 会触发 k 次 clone（O(n·k)）。
- 实证代价（Go，2 万键命名空间）：单键 put 均摊 9.5ms（含全量落盘，clone 为其中固定开销）。
- 修复：引入快照计数/版本号，仅在有存活快照时 clone（与 Rust 语义对齐）。

### P1-6（新）：.NET 命名空间排序器违反 §4.3.1（`StringComparer.Ordinal` = UTF-16 序）

- 规范明确"严格禁止使用默认 SortedDictionary，必须显式注入基于 compareUtf8Bytes 的 IComparer<string>"。
- .NET `Db.cs:85-86` 用的正是 `StringComparer.Ordinal`（UTF-16 码元序）。对含辅助平面字符（emoji 等）的命名空间名，UTF-16 序与 UTF-8 字节序**相反**。
- 讽刺的是 `Utf8ByteComparer` 类就写在 `BinaryHelper.cs:101` 里却没人用。
- 落盘时 `flushSnapshot` 另做了 UTF-8 排序（正确），所以磁盘没错，但内存迭代序与磁盘序会分叉。
- 修复：一行替换为 `Utf8ByteComparer` 对应的 string 比较器（需按 UTF-8 字节比较 namespace 字符串）。

### P1-7（新）：Go `KeyChangeOp` 数值体系错误（iota 从 0 起）

- 见 P0-5，即使补齐 DropNamespace/Clear，Go 的 `Put=0/Delete=1` 也与规范/另两种语言的 1/2/3/4 冲突，必须显式赋值。单列强调是因为这是"补枚举时最容易再次搞错"的坑。

## 七、架构层面确认没问题的部分（不要动）

1. **磁盘二进制格式**：32B 头 + 28B 帧头 + 贪心装箱（`OpCount>=1M || payload+entry>64MB`）+ 默认命名空间 `NsLen=0` + `"default"` 保留别名 + 空库 32B + TxID 单调——三语言字节级一致，黄金向量与 interop 闭环全绿。
2. **CRC32**：三语言内联查表实现一致，标准向量 `0xCBF43926` 通过。
3. **CoW 快照**：Rust `Arc<BTreeMap>` + `make_mut`、Go 浅克隆替换、.NET 不可变 `KeyItem` + `Clone`——读无锁、写不阻塞快照，`Snapshot` 完全脱离主锁。
4. **Watcher 防死锁铁律**：事件写锁内收集、锁外派发，三语言一致，回调内重入读安全。
5. **两代原子轮转 + 崩溃恢复链**：`.tmp` 晋升 → 主库全帧校验失败回退 `.bak` → 主备双坏拒绝静默清空。
6. **阶段一写放大**：已知设计取舍（benchmark 报告已量化），阶段二设计文档已就绪——列为已知限制即可，不是 bug。

## 九、结论

- **磁盘格式与并发内核可以放心**，这是项目最值钱的部分，无需改动。
- **API 表层目前不能算稳定**：本文新实证的 4 个 P0（Rust 类型拦截缺失、.NET 加载器缺删除重放/TxID 校验）+ 第一轮的 B1/A1-A5，合计 8 项 P0。此时冻结 API，等于把"Rust 的 get_string 返回乱码"、"Go 的 watcher 事件数值对不上"这类形态固化进 7 种语言，v2 再做破坏性修复的成本翻倍。
- 按第八节顺序执行，**预计一周内完成 P0+P1 并冻结 API v1.0**，随后启动 Python/Node/Dart/Kotlin 与公开发布是合理路径。
