# CKV 三语言实现（Rust / Go / .NET）代码与架构审查报告

> 审查日期：2026-10-15
> 审查范围：`src/rust`、`src/go`、`src/dotnet` 三套实现的源码、二进制格式合规性、跨语言 API 一致性、崩溃恢复与并发模型。
> 配套规范：`docs/KV-DB-DESIGN-SPEC.md`（v3.2）

---

## 一、总体结论

| 维度 | 结论 |
| :--- | :--- |
| **磁盘二进制格式（v3.2）** | ✅ 扎实、跨语言互通已通过黄金向量与 interop 测试，是整套设计里最成熟的部分 |
| **进程内内存模型 / 快照 CoW / Watcher 防死锁** | ✅ 三语言设计到位，思路一致 |
| **进程内 API 表面一致性** | ⚠️ 存在 1 个**已实锤的严重自触发崩溃 bug**，以及多处**跨语言 API 不一致** |
| **是否可立即冻结 API 并启动 Python/Node/Dart/Kotlin** | **不建议**。先把下面「必须修复项」处理完再冻结，否则新语言会继承错误形态，或被迫在 v2 做破坏性变更 |

**一句话**：文件格式可以放心继续用；内存 API 还不能算"稳定"，建议先修 bug + 对齐契约，再开新语言端口与公开发布。

## 二、已实锤的严重 Bug（必须修）

### B1（严重）：清空库后再次写入，同实例内自触发 `ConcurrentModificationError`

- **复现路径**：`put` → `clear_namespace("")` → 再次 `put`（同一个已打开的实例）。
- **实测证据**：
  - Go：`go test` 输出 `ConcurrentModificationError: Disk state changed externally: expected (1, 32), found (0, 32)`。
  - Rust：`cargo test` 输出 `ConcurrentModification("Disk state changed externally: expected (1, 32), found (0, 32)")`。
- **根因**：§4.1.3 的「写前磁盘状态预检」把内存记录的 `last_known_disk_state = (txid, 32)` 与磁盘扫描结果对比。清空后磁盘是合法的 32 字节空文件（无帧），`scan_max_tx_id` 返回 `0`，于是 `0 != 1` 被判为"外部修改"。
- **影响**：任何「清空后再写」的正常用法都会崩溃。现有测试未覆盖此路径（大多数是 `clear` 之后 `close` 再 `reopen`，重开后 `last_known=(0,0)` 不触发）。
- **修复建议**：预检时，若磁盘文件为空文件（恰 32 字节、无帧），只比较 `file_size`，不要比较 `txid`（空文件无法在磁盘上表达 txid）。或令 `scan_max_tx_id` 对空文件返回内存期望值 `currentMaxTxID`。
- **波及**：Rust、Go 的 `flush_snapshot` 都有此逻辑，需同步修；.NET 因未实现 §4.1.3 预检（见 A5）反而不受此 bug 影响。

## 三、跨语言 API 不一致（冻结前必须统一）

### A1：`KeyChangeOp` 只有 2 个变体（Rust / Go），缺 `DropNamespace(3)` 与 `Clear(4)`

- 规范 §5.2.3 明确定义 4 个：`Put=1, Delete=2, DropNamespace=3, Clear=4`。
- .NET 的 `KeyChangeOp` 枚举是 4 元；Rust 的 `KeyChangeOp` 只有 `Put, Delete`；Go 的 `OpChangePut, OpChangeDelete` 只有 2 个。
- 后果：Rust/Go 的 `drop_namespace`、`clear_namespace`、以及 batch 中对应操作，全部发出 `Delete(2)` 事件。订阅者无法区分「删键 / 删命名空间 / 清空命名空间」。若新语言按规范的 4 元实现，会与旧语言 writer 的事件语义错位。
- **动作**：Rust/Go 补齐枚举到 4 元，并在 `drop_namespace` / `clear_namespace` / batch 中发出正确的 op。

### A2：`delete` / `drop_namespace` / `clear_namespace` 返回值不一致

- 规范：三者均返回 `bool`（是否实际影响/命中）。
- 现状：.NET 返回 `bool`（✓）；Rust `delete -> Result<()>`（内部算了 `existed` 却丢弃）；Go `Delete -> error`（只有错误，无布尔）。
- **动作**：统一为返回 `bool`。

### A3：`batch.clear_namespace` 在高阶批处理 API 中缺失（Rust / Go）

- 规范 / README / CHANGES 均明确要 `batch.clear_namespace(ns)`。
- 现状：.NET `BatchWriter.ClearNamespace` 已实现（✓）；**Rust `BatchOp` 枚举无此变体、Go `BatchWriter` 无此方法**。
- **动作**：Rust/Go 补齐 batch 级 `clear_namespace`。
- 备注：独立的 `clear_namespace` 方法三语言都有，仅"批处理内"版本缺失。

### A4：锁文件 32 字节二进制布局，.NET 与规范 / Rust / Go 不一致

- 规范 §4.1.2：`0..8 PID(uint64_le) | 8..24 LockUUID(16B) | 24..32 CreateTimeMs(uint64_le)`。Rust / Go 符合。
- .NET `LockFile` 实际写入：`0..4 PID(uint32) | 4..20 UUID(16B) | 20..28 CreateTimeMs`，整体偏移 4 字节。
- 后果：跨语言进程锁文件**字节不兼容**（虽然多进程并发写入本就不支持，但 stale-lock 恢复、以及未来的多进程场景会出问题；且 .NET 自身的 ABA 释放校验读取偏移 `[4..20]` 与 Rust/Go 的 `[8..24]` 不同）。
- **动作**：三语言统一对齐到 §4.1.2 布局（PID 用 uint64）。

### A5：§4.1.3 并发修改预检三语言不齐

- Rust / Go 实现了预检（但带 B1 bug）；**.NET `FlushSnapshot` 完全没有做预检**（不会抛 `ConcurrentModificationError`）。
- **动作**：统一决策——要么三语言都实现（复用 B1 修复后的空文件处理），要么都在文档显式声明"不实现 / unsupported"。推荐前者，与规范一致。

## 四、建议明确文档化的事项（非阻塞，但发布前要有说法）

1. **`increment_i64` 溢出语义**：Rust `wrapping_add`、.NET `unchecked`、Go `int64` 自然回绕。明确写入文档「溢出按补码绕回」。
2. **`Snapshot.ScanRange` / `Keys` 签名**：Go 里 `DB.ScanRange` 用 `*string`、`Snapshot.ScanRange` 用 `string`；Rust 统一 `Option<&str>`。API 文档需给出统一语义描述。
3. **`get*` 错误传播风格**：Rust 返回 `Result`、.NET 抛异常、Go 返回 `(ptr, error)`。按语言习惯保留，但**错误名必须统一为规范 9 个**（`CorruptedError`/`LockedError`/`ConcurrentModificationError`/`InvalidUtf8Error`/`TypeMismatchError`/`KeyTooLargeError`/`InvalidNamespaceError`/`UnsupportedVersionError`，基类 `DbError`）。
   - 现状：Rust 用 enum 变体、Go 用单错误 + `Type` 字符串、.NET 用异常子类。名称已对齐即可，文档说明差异。
4. **会话锁语义**：当前 `.lock` 在**每次 `flush` 时获取/释放**，并非整个会话持有。多进程并发读写明确不支持（§1.1）。文档需显式说明此边界。
5. **写放大（已知限制）**：stage-1 每次写入都全库快照重写（`O(total DB)`），库 >10MB 后写延迟随库大小线性增长——benchmark 报告已记录。这是设计取舍，列为已知限制；stage-2 追加写 WAL + 后台 Compaction 是后续增强（见 `docs/PHASE2-APPEND-LOG-COMPACTION-DESIGN.md`）。
6. **README 矩阵过时**：用户计划加 Dart / Kotlin，但矩阵里只有 Python / Node.js / Java。需补充 Dart、Kotlin 行，并标注状态。

## 五、架构优点（确认没有问题的部分）

- **纯原生零依赖**：三语言 100% 标准库，内联 IEEE 802.3 CRC32 一致（黄金向量 `0xCBF43926`、空库 `0x0C44C937`、单条 `0x501DB93E`/`0x59CBDB33` 全部通过）。
- **二进制格式确定性**：帧头 28B、帧载荷贪心装箱（`OpCount>=1_000_000 || payload+entry > 64MB`）、默认命名空间 `NsLen=0`、`"default"` 保留别名、空库 32 字节、TxID 单调——三语言一致，interop 测试通过。
- **快照 CoW 设计到位**：
  - Rust：`BTreeMap<Vec<u8>, Arc<BTreeMap<...>>>` + `Arc::make_mut` 写时复制；
  - Go：`namespaceStore` 浅克隆后替换指针；
  - .NET：不可变 `KeyItem` + `NamespaceStore.Clone()`。
  - 三者都实现「读无锁、写不阻塞快照、Snapshot 完全脱离 RwLock」。
- **Watcher 防死锁铁律**：事件在写锁内收集、写锁释放后派发——三语言一致，回调内重入读安全。
- **崩溃恢复链路完整**：`.tmp` 晋升 → 主库全量校验失败回退 `.bak` → 主备双坏拒绝静默清空。
- **进程内单例注册表**（Rust / .NET）防止同路径重复 `open` 造成内存分化与写锁踩踏。

## 六、发布前行动建议（推荐顺序）

1. **修 B1（紧急）**：Rust / Go 的 §4.1.3 预检处理空文件（32 字节）场景，消除自触发崩溃。
2. **对齐 API 契约（A1–A5）**：4 元 `KeyChangeOp`、`delete/drop/clear` 返回 `bool`、batch 版 `clear_namespace`、锁文件布局对齐 §4.1.2、§4.1.3 预检三语言统一。
3. **补回归测试**：增加「清空/删空后同实例再写」等用例，防止 B1 类回归；补齐 Rust/Go 的 batch clear 测试。
4. **冻结 API 契约 + 更新文档**：锁定方法签名、9 个错误名、4 元 Watcher op、返回值；更新 README 矩阵（Python/Node/Dart/Kotlin）与 API 文档，写明已知限制（写放大、多进程不支持、锁为每-flush 级）。
5. **启动新语言端口**：严格按冻结的 API 契约 + v3.2 二进制规范实现 Python / Node / Dart / Kotlin，复用既有黄金测试向量与 interop 测试作为验收门槛。
6. **公开发布**：含上述已知限制说明。
