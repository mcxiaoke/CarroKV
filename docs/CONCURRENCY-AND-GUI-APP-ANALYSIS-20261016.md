## 第一部分：CKV 内部多线程与并发控制机制核对

### 1.1 进程内读写锁实现对比

根据 [KV-DB-DESIGN-SPEC.md §4.1.1](file:///c:/Home/Projects/ckv/docs/KV-DB-DESIGN-SPEC.md#L4.1.1) 的线程安全规范，各语言实现均在进程内维护了读写锁控制并发访问：

| 语言 | 锁类型 | 句柄封装 | 线程安全属性 |
| :--- | :--- | :--- | :--- |
| **Rust** | [`parking_lot::RwLock<DbInner>`](file:///c:/Home/Projects/ckv/src/rust/src/db.rs#L74) | `Db { inner: Arc<RwLock<DbInner>> }` | `Send + Sync + Clone` |
| **Go** | [`sync.RWMutex`](file:///c:/Home/Projects/ckv/src/go/db.go#L68) | `*DB` | 内部加锁，goroutine 并发安全 |
| **.NET** | [`System.Threading.ReaderWriterLockSlim`](file:///c:/Home/Projects/ckv/src/dotnet/src/Ckv/Db.cs#L83) | `CkvDb` 实例 | 内部加锁，多线程并发安全 |

### 1.2 实例注册表与多重打开语义

当同进程内不同线程针对同一文件路径执行打开操作时，三语言实现存在差异：

- **Rust (`src/rust/src/db.rs`)**：
  维护全局静态注册表 [`SHARED_REGISTRY`](file:///c:/Home/Projects/ckv/src/rust/src/db.rs#L16)（类型为 `Mutex<Option<HashMap<PathBuf, Weak<RwLock<DbInner>>>>>`）。
  并发线程对同一规范路径调用 `Db::open` 时，若现有实例存活，直接通过 `Weak::upgrade` 返回指向同一锁的 `Db` 实例克隆，共享同一内存状态与锁。
- **.NET (`src/dotnet/src/Ckv/Db.cs`)**：
  维护全局静态注册表 [`Registry`](file:///c:/Home/Projects/ckv/src/dotnet/src/Ckv/Db.cs#L77)（类型为 `ConcurrentDictionary<string, WeakReference<CkvDb>>`）。
  并发线程对同一路径调用 `CkvDb.Open` 时，返回同一实例引用，共享 `_rwLock`。
- **Go (`src/go/db.go`)**：
  当前未维护全局实例注册表（见 [GAP-ANALYSIS-20261015.md:97](file:///c:/Home/Projects/ckv/docs/GAP-ANALYSIS-20261015.md#L97)）。
  若不同 goroutine 分别调用 `ckv.Open(path)`，将在内存中创建两个相互独立的 `*DB` 实例。两实例各有一把 `sync.RWMutex`，写盘时通过文件锁 `.lock` 排他，后写入者会触发 `ConcurrentModificationError`。在 Go 中应由调用方统一持有单个 `*DB` 指针并发复用。

### 1.3 读、写、快照与 Watcher 的锁边界

#### A. 读操作（Read Path）
- 调用的锁级别：**共享读锁**（Rust `inner.read()`、Go `db.mu.RLock()`、.NET `_rwLock.EnterReadLock()`）。
- 操作范围：仅读取内存中有序结构（Rust `BTreeMap`、Go `namespaceStore`、.NET `SortedDictionary`）。
- I/O 开销：0 次系统调用，0 次磁盘 I/O。
- 并发度：任意数量读线程完全并行，无互斥等待。

#### B. 写操作（Write Path）
- 调用的锁级别：**独占写锁**（Rust `inner.write()`、Go `db.mu.Lock()`、.NET `_rwLock.EnterWriteLock()`）。
- 操作范围（阶段一整库轮转模型）：
  1. 获取写锁；
  2. 获取跨进程 `.lock` 文件，校验磁盘 `(MaxTxID, FileSize)` 预检版本；
  3. 修改内存键值结构；
  4. 序列化全量数据写入临时文件 `.tmp`；
  5. 调用 `fsync` 确保落盘；
  6. 原子替换（`.tmp` -> `.db`，旧库变为 `.bak`）；
  7. 释放 `.lock` 文件；
  8. 拷贝待派发的 Watcher 事件列表，**退出写锁**。
- 并发度：写写互斥，写读互斥。

#### C. 快照操作（Snapshot Path）
- 创建阶段：瞬时获取读锁（或在写锁内登记），执行写时复制（CoW）引用计数复制（Rust 复制 `Arc<BTreeMap>`，Go/C# 复制命名空间引用），随后立即释放主库锁。
- 读取阶段：快照对象上的读取（`snapshot.get_*`、`snapshot.scan_range` 等）**不获取主库的任何读写锁**。
- 并发度：快照读与主库的写入互不阻塞。主库写入若遇到存活快照，执行命名空间级别拷贝（CoW），不影响快照读取。

#### D. 变更监听器（Watcher / KeyChanged）
- 约束：派发逻辑严格在**写锁完全退出之后**执行。
- 目的：避免调用方在回调函数中再次调用 `db.get_*` 或 `db.put_*` 时因重入写锁引发死锁。

### 1.4 多线程读写的实际执行行为分析

| 场景 | 执行机制 | 行为表现 |
| :--- | :--- | :--- |
| **并发只读** | 多线程同时获取读锁 | 完全并发，无锁竞争，点查平均延迟 400ns ~ 1.5µs |
| **并发写入** | 多线程竞争独占写锁 | 严格排队串行化执行，单次写完成后释放写锁给下一个等待线程，数据不冲突 |
| **读写并发** | 写线程持有写锁期间，读线程等待读锁 | 保证读取强一致性（无脏读），但读操作会被阻塞直到写盘与轮转完成 |
| **快照读与写并发** | 快照读不申请主库锁，写线程申请写锁 | 双方互不等待，快照读取保持创建时点的一致性，写线程通过 CoW 分离数据 |
| **Watcher 回调重入** | 回调在写锁退出后触发 | 回调内再次调用 `db.get` 或 `db.put` 不会发生死锁，按普通读写请求重新争锁 |
| **多线程重复 Open** | Rust/.NET 返回共享实例；Go 返回新实例 | Rust/.NET 表现为同一进程内共享锁；Go 若多实例并发写，后写者报 `ConcurrentModificationError` |

## 第二部分：GUI 客户端应用场景分析与主流存储方案技术对比

### 2.1 客户端运行环境的技术约束

在 Windows 桌面端（.NET/WPF/WinUI）、跨平台框架（Flutter/React Native）及移动端（Android/iOS）中，存储层面临以下硬件与系统调度约束：

1. **渲染帧率约束**：
   UI 渲染周期为 16.6ms（60Hz）或 8.3ms（120Hz）。UI 主线程执行超过 16ms 的同步阻塞操作会引起掉帧；Android 超过 5 秒未响应报 ANR 强退，iOS 触发看门狗（Watchdog）崩溃。
2. **生命周期突发终止**：
   移动端应用切至后台后，系统在内存吃紧时通过 `SIGKILL` 终止进程；用户划卡退出同样不触发析构函数或 `Close()`。
3. **闪存写入耐久度（P/E Cycles）**：
   移动设备与嵌入式存储（UFS / eMMC / MicroSD）对高频小写入较为敏感，高写入放大将加速闪存寿命磨损并产生额外耗电与发热。
4. **进程内存配额（RAM Quota）**：
   移动端低端设备内存上限较小（部分 Android 设备堆限制为 192MB/256MB，iOS Widget / Extension 限制为 30MB 左右）。
5. **多进程与扩展架构**：
   iOS 主 App 与 Today Widget / Notification Service Extension 属于不同进程，需通过 App Group 共享文件；Android 常见推送 Service 与主进程分离。
6. **动态库打包与 ABI 复杂度**：
   依赖 C/C++ 动态库（`.so`/`.dylib`/`.dll`）需要编译多种目标架构（Android 4 种 ABI，iOS 真机/模拟器），增加构建复杂性与安装包体积。

### 2.2 CKV 架构在客户端环境的技术特征与实测数据

根据 [BENCHMARK-STAGE1-EVALUATION.md](file:///c:/Home/Projects/ckv/docs/BENCHMARK-STAGE1-EVALUATION.md) 的实测数据，CKV 当前架构（阶段一全量快照轮转）在客户端场景下的表现如下：

#### A. 写入耗时与帧率影响
阶段一写入逻辑为：全量内存序列化 $\rightarrow$ 计算 CRC32 $\rightarrow$ 写入 `.tmp` $\rightarrow$ `fsync` 刷盘 $\rightarrow$ 原子替换重命名。

实测写入耗时：
- **1.02 MB 库（500 条数据）**：单键写入平均耗时 **7.08 ms**（写放大 1,039 KB）；
- **9.78 MB 库（5,000 条数据）**：单键写入平均耗时 **42.37 ms**（写放大 10,019 KB）；
- **98.27 MB 库（50,000 条数据）**：单键写入平均耗时 **367.03 ms**（写放大 100,632 KB）。

在移动端闪存（UFS/eMMC）与弱算力 ARM CPU 推演：
- 9.78 MB 库单键写耗时推演为 **80 ~ 150 ms**；
- 98.27 MB 库单键写耗时推演为 **1.2 ~ 2.5 秒**。

**影响**：若在 GUI 主线程同步调用写操作，数据量大于 5MB 时单次写入耗时超过 16.6ms，直接导致界面掉帧。

#### B. 读延迟长尾分布
在 4 线程混沌测试（4 线程并发执行 10,000 次操作，含 60% 读与 15% 写）中：
- 内存点查 P50：**1.50 µs**；
- 内存点查 P95：**15.8 ms**；
- 内存点查 P99：**41.0 ms**；
- 内存点查 Max：**165.2 ms**。

**影响**：由于写操作在持有独占写锁期间执行了整库序列化与 `fsync`，读线程在写盘期间被阻塞排队，导致点读 P99 出现长尾延迟。

#### C. 冷启动与反序列化
- 高端 PC（.NET 8，16 线程）：98.27 MB 库冷启动读取并建树耗时 **294.2 ms**；
- 低功耗单核 Linux（Pentium G3260T）：88 MB 库（50,000 条数据）冷启动读取建树耗时 **76.4 秒**。

**影响**：低算力单核环境下，全量一次性反序列化与红黑树/字典节点分配会消耗较多 CPU 时间。

#### D. 进程终止安全性
- 采用 `.tmp -> .bak -> .db` 轮转。若进程在写 `.tmp` 时被 `SIGKILL`，正式 `.db` 未被修改，启动时清理未竟 `.tmp`；若在替换后崩溃，存在 `.bak` 可供恢复。
- 实测无文件帧撕裂损坏风险。

#### E. 多进程支持
- 依赖单写者 `.lock` 文件互斥。主 App 与小组件同时发起写操作时，一方会因锁冲突抛出 `LockedError` 或 `ConcurrentModificationError`；
- 数据全量缓存于进程内存，一进程落盘后，其他常驻进程不会主动感知磁盘变更。

### 2.3 主流嵌入式 KV 与数据库技术方案对比

| 技术维度 | CKV (阶段一整库轮转) | MMKV (微信) | SQLite (WAL 模式) | Hive / Isar (Flutter) |
| :--- | :--- | :--- | :--- | :--- |
| **存储原理** | 内存红黑树/字典 + 全量磁盘帧轮转 | 内存操作映射到 `mmap` 文件页 | 页式 B-Tree + Append-Only WAL 日志 | 内存索引 + 追加日志 (Box) |
| **点读延迟** | **400ns ~ 1.5µs**（纯内存结构） | **微秒级**（指针直接读虚拟内存） | 亚毫秒级（走页缓存查找） | 微秒级（内存索引） |
| **单写机制** | 同步全量序列化 + `fsync` 刷盘 | 写入虚拟内存页，内核异步调度刷盘 | 向 WAL 追加修改页与提交帧 | 向文件末尾追加二进制数据 |
| **单写延迟** | 7ms ~ 367ms（随整库体积线性增长） | **微秒级**（无显式磁盘系统调用） | 亚毫秒级 ~ 毫秒级（只写差异页） | 毫秒级（顺序追加写） |
| **写放大** | **$O(TotalDB)$**（改 1 字节写整库） | 极低（仅更新被修改的内存页与日志）| 较低（仅写入变更的 4KB 数据页） | 接近 $1\times$（仅追加当前条目） |
| **UI 线程调用** | 读可以，写**严禁**在 UI 线程执行 | 可直接在 UI 线程执行读写 | 建议放入后台线程（Room 强制拦截） | 推荐异步 Isolate 调用 |
| **多进程支持** | 仅单进程互斥，不支持多进程写 | **支持**（跨进程 mmap + 页头版本号）| **支持**（`.db-shm` 共享内存协议）| 不支持（单进程独占） |
| **跨语言互通** | **跨语言统一二进制无损互读互写** | 多语言实现独立，主要在各端原生使用 | 统一 `.db` 二进制，全平台通用 | 强绑定 Dart 生态 |
| **Native 依赖**| **零依赖**（各语言纯托管/标准库） | 依赖 C++ Native 动态库 | 依赖 C Native 动态库 | 依赖 C/Rust Native 动态库 |
| **内存占用** | 全量常驻内存（数据量大时占用较高）| 依赖操作系统分页置换（适中） | 页缓存可控（可设定上限，默认几 MB）| 索引常驻，数据按需读取 |

### 2.4 技术选型与工程使用边界

基于上述数据与特性，CKV 在 GUI 客户端中的技术定位与使用建议如下：

#### A. 适用场景（推荐）
1. **应用全局配置与偏好设置（Settings / Preferences）**：
   替代 XML/JSON/SharedPreferences，库体积通常小于 5MB，单写耗时小于 10ms，常驻内存读取为纳秒级。
2. **用户认证凭据与状态机（Session / Token / State）**：
   利用其强类型校验、原子替换与 `.bak` 自愈能力，保证凭据在异常断电时不丢失、不损坏。
3. **跨语言桌面客户端架构**：
   例如核心引擎采用 Rust/Go 编写、UI 采用 C# WPF / WinUI 编写的桌面应用，双方直接无损共享访问同一个 `.db` 文件，免除跨进程 IPC 反序列化。

#### B. 不适用场景（当前阶段不推荐）
1. **海量聊天记录、离线邮件与大文本库（> 50MB）**：
   全量内存常驻会占用较多客户端 RAM，整库序列化落盘开销过大；此类场景应选用 SQLite。
2. **高频写入场景（如高频埋点、传感器采样、打字实时保存）**：
   单写触发整库重写会导致写放大严重并磨损闪存；应选用追加写（WAL）方案或在应用层合批。
3. **需要与 iOS Extension / Android 多进程无缝互通的场景**：
   由于缺乏跨进程共享内存机制，进程间无法感知内存更新。

#### C. GUI 开发最佳工程实践
1. **写操作后台化**：
   避免在 UI 主线程执行 `Put`、`Batch`、`Delete`，在 .NET 中使用 `Task.Run`，在 Flutter 中放入 `Isolate`，在 Android 中调度至 `Dispatchers.IO`。
2. **聚合写入（Batching）**：
   多次连续修改使用 `db.Batch(...)`，将多次全量落盘压缩为一次原子写。
3. **长耗时扫描使用 Snapshot**：
   对数据做统计或遍历展示时，调用 `db.Snapshot()`，使用快照遍历避免阻塞写线程或被写锁阻塞。
4. **单实例 App 启用 ForceUnlock**：
   客户端单实例启动时，配置 `DbOptions { ForceUnlock = true }`，防止应用被杀后快速重启遇到残留锁等待。

## 第三部分：针对中小规模（< 20MB）GUI 客户端的高可靠优化方案

### 3.1 排除大体积与海量场景后的核心瓶颈重定义

当明确将应用场景收敛在 **单库体积 < 20MB（典型分布为 100KB ~ 5MB）、条目数在几十条至数千条** 时，先前针对海量数据的多项技术挑战在客观上不再构成阻碍：

1. **内存开销不再是瓶颈**：10MB 的二进制数据展开到托管堆内存约为 20MB ~ 30MB，远低于移动端进程的 OOM 警戒线（Android 常见限制为 192MB ~ 512MB）；
2. **冷启动不再是瓶颈**：基准实测表明，1.02MB 库启动校验建树耗时为 3.8ms，9.78MB 库为 39.7ms，均处于客户端启动时间预算（< 400ms）之内；
3. **架构演进排除项**：在此场景下，**无需**引入重型的 Append-Only WAL、LSM 多路归并排序、冷热数据分页置换（Page Cache）以及常驻文件句柄等高复杂度机制，从而避免破坏“纯托管、跨语言统一二进制、零副作用自愈恢复”的核心架构资产。

在中小规模场景下，客户端暴露的实际核心瓶颈收敛为以下两点：
- **读写锁互斥导致 UI 读操作被写盘长尾阻塞**：单写虽仅需 7ms ~ 42ms，但因写锁全程持有着执行磁盘落盘，导致同周期的 UI 读线程出现 P99 达 41ms ~ 165ms 的掉帧卡顿；
- **高频界面事件触发过多整库全量刷盘**：连续输入、滑块拖动产生多次写操作，在无防抖聚合时触发重复整库序列化与 `fsync`，消耗 CPU 算力并加剧闪存磨损。

### 3.2 高可靠优化方案一：写锁范围缩容（读写解耦，消除 UI 读卡顿）

#### 1. 现状执行路径与开销
当前写入路径中，独占写锁的持有范围包含全量 I/O：
```
写锁持有区间：[ 内存树修改 (1~3µs) + 全量序列化 (0.5~5ms) + 写.tmp与fsync (5~35ms) + 重命名轮转 (1~3ms) ]
```
写锁持有时间为 7ms ~ 42ms。在此期间，UI 主线程发起的任何 `db.get_*` 均处于阻塞挂起状态。

#### 2. 改进方案：基于已有的 CoW 机制拆分锁粒度
CKV 各语言在实现 `Snapshot` 时，内部命名空间已采用写时复制（CoW）结构（Rust 为 `Arc<BTreeMap>`，Go 为 `namespaceStore.clone()`，.NET 为命名空间字典浅拷贝）。可直接复用该机制将写路径解耦为两段：

1. **第一阶段：内存指针原子切换（持写锁，耗时 < 5 微秒）**
   - 获取主库写锁；
   - 递增 `current_max_tx_id`；
   - 对目标命名空间执行 CoW 克隆并插入新键值；
   - 获取当前最新内存状态的只读引用（`RootStateRef`）；
   - **立即退出写锁**。
2. **第二阶段：后台排他序列化与落盘（持独立的 `flush_mutex`，不持有主库读写锁）**
   - 获取专用磁盘落盘互斥锁 `flush_mutex`（仅用于串行化多次写盘任务，不阻塞任何读操作）；
   - 基于步骤 1 捕获的不可变 `RootStateRef`，在锁外执行序列化、写 `.tmp`、`fsync` 与原子重命名；
   - 更新 `last_known_disk_state`；
   - 派发 Watcher 事件；
   - 释放 `flush_mutex`。

#### 3. 实测数据预期与可靠性
- **预期收益**：UI 线程的 `db.get_*` 与写操作竞争锁的时间由 7ms ~ 42ms 压缩至 5µs 以内，点查 P99 延迟回归至 1.5µs 水平，彻底消除并发写引发的 UI 读卡顿；
- **可靠性保证**：完全保持 v3.2 二进制文件格式、两代轮转 `.tmp -> .bak -> .db` 及启动自愈机制不变；若落盘出现 I/O 错误，由于内存状态已分叉，可将实例置为降级只读状态或标记持久化失败异常，避免静默数据丢失。

### 3.3 高可靠优化方案二：定时防抖与自动批聚合落盘（Debounced Flush）

#### 1. 针对 GUI 交互的写入特征
客户端配置变更通常呈现“脉冲式”密集触发（例如：用户连续键入搜索词、滑动调节音量/窗口大小、快速切换 Tab 页）。每次微小修改均触发一次全量序列化与刷盘属于无效 I/O。

#### 2. 改进方案：可选防抖延迟刷盘
在保持现有 API 默认立即同步落盘（向后兼容）的前提下，在 `DbOptions` 中增加延迟刷盘配置：

```csharp
// 配置示例 (.NET)
var options = new DbOptions
{
    FlushDelayMs = 150,  // 写入后延迟 150ms 落盘（防抖窗口）
    MaxPendingWrites = 50 // 或累积 50 次写入强制落盘
};
```

1. **防抖执行逻辑**：
   - 调用 `put_*` 或 `delete` 时，仅在内存中执行微秒级更新并更新脏标记（Dirty Flag），重置轻量定时器（Timer）；
   - 若在 150ms 窗口期内有新的写入，直接在内存累积并续订定时器；
   - 当静默期满或达到最大待刷盘计数（`MaxPendingWrites`）时，后台触发一次批量全量落盘。
2. **生命周期兜底机制（防丢数据）**：
   - 增加显式接口 `db.flush()`；
   - 接入客户端生命周期事件：
     - **iOS**：在 `UIApplication.didEnterBackgroundNotification` 时调用 `db.flush()`；
     - **Android**：在 `Activity.onPause()` / `onStop()` 时调用 `db.flush()`；
     - **Windows (.NET)**：在 `AppDomain.CurrentDomain.ProcessExit` 或 `FormClosing` 中调用 `db.flush()`；
   - `db.close()` / `Dispose()` 自动执行同步强刷。

#### 3. 实测数据预期与可靠性
- **预期收益**：连续 100 次高频输入在 1 秒内由 100 次磁盘落盘合并为 1~2 次落盘，写放大减少 98% 以上，UI 线程调用延迟由毫秒级降至微秒级；
- **可靠性保证**：纯进程内调度优化，不修改底层存储协议。

### 3.4 高可靠优化方案三：未修改命名空间缓存复用（脏标记跳过重编码）

#### 1. 现状开销
在典型中小库中，用户通常会划分多个命名空间（如 `app_settings` 4KB、`window_state` 1KB、`user_profile` 8KB、`ui_cache` 2MB）。
当前无论修改哪个命名空间，全量落盘时都会遍历所有命名空间中的全部条目，重新进行二进制打包并重新计算每帧 CRC32。

#### 2. 改进方案：命名空间级二进制切片缓存（Namespace Frame Cache）
1. 每个命名空间维护一个 `is_dirty: bool` 标记及该命名空间上次成功落盘生成的已编码字节切片 `cached_frames: Vec<u8>`；
2. 当某次写操作仅修改了 `window_state` 时，仅将该命名空间标记为 dirty；
3. 落盘写 `.tmp` 时：
   - 对于未被修改的命名空间（`!is_dirty`），直接将预先编码好的 `cached_frames` 写入文件流，跳过条目遍历、字符串 UTF-8 校验与帧装箱计算；
   - 仅对 `is_dirty` 的命名空间执行全量帧重编码，并更新其缓存切片；
   - 文件尾部全库校验和仍统一计算。

#### 3. 实测数据预期与可靠性
- **预期收益**：在多命名空间场景下，局部小写操作的 CPU 序列化与内存分配开销降低 50% ~ 70%；
- **可靠性保证**：输出的二进制帧流与全量重编码产物完全一致，跨语言文件格式 100% 兼容。

### 3.5 高可靠优化方案四：客户端响应式数据流适配（UI 局部自动刷新）

#### 1. 现状与客户端开发摩擦
当前 CKV 提供 `Watch(callback)` 机制，但客户端 UI 框架（WPF、Flutter、React Native）普遍采用响应式状态绑定。调用方需自行编写胶水代码将回调桥接至 UI 线程，容易引发线程调度错误或重复轮询。

#### 2. 改进方案：在各语言端侧封装轻量绑定库
基于现有的锁外 Watcher 事件派发机制，在各语言 SDK 顶层提供原生响应式包装：

- **.NET (C# / WPF / MAUI)**：
  - 提供 `BindableProperty<T>` 封装，自动实现 `INotifyPropertyChanged`，底层监听到特定 Key 变更时自动通过 UI 调度器（`SynchronizationContext`）触发属性变更通知，直接驱动 XAML 双向绑定。
- **Flutter (Dart)**：
  - 提供 `ValueListenable<T>` 封装，当底层键值修改时通知监听者，与 `ValueListenableBuilder` 局部组件刷新完全吻合，避免全树重绘。
- **React Native (JS/TS)**：
  - 基于 React 18+ 的 `useSyncExternalStore` 封装 `useCkvKey(ns, key)` Hook，组件按需订阅键值变更。

### 3.6 方案可靠性与风险边界评估

| 优化方案 | 修改代码层级 | 跨语言格式兼容性 | 潜在风险（Failure Mode） | 防御与兜底机制 |
| :--- | :--- | :--- | :--- | :--- |
| **方案一：写锁范围缩容** | 核心引擎读写锁调度 | 100% 兼容（格式无变动） | 内存已更新但磁盘落盘失败（分叉状态） | 落盘失败时记录致命错误状态，阻止后续写入并通知调用方，保持一致性 |
| **方案二：防抖批落盘** | 核心引擎配置与定时器 | 100% 兼容（格式无变动） | App 被 `SIGKILL` 强杀时丢失最后 150ms 内未刷盘数据 | 默认关闭（保持强同步）；提供 `db.flush()` 挂接切后台生命周期事件 |
| **方案三：命名空间切片缓存** | 序列化写入管线 | 100% 兼容（产物字节完全一致）| 脏标记遗漏导致落盘产物未包含最新数据 | 任何写路径强制标记目标命名空间为 dirty，内存状态版本与切片严格绑定 |
| **方案四：响应式数据绑定** | 上层 SDK 语言封装 | 无关（属于上层应用逻辑） | 监听器回调内部异常导致 UI 崩溃 | 严格在 UI 线程调度分发前捕获异常，并沿用锁外派发机制防死锁 |
